# 可选的运行持续推进

持续推进为没有正常执行者的 Work 提供有限次数的主管唤醒。默认关闭；旧配置、旧数据以及普通任务通知继续按 H1 工作。它不判断代码是否正确，不替 agent 接受任务，也不自动批准计划或落地。

## 开启与查看

GUI：首页创建 Work → 更多选项 →「停滞时唤醒主管」，设置整个 Work 的最多唤醒次数和等待间隔。默认值为 3 次、60 秒；选择全托管本身不会开启此功能，也不会改变落地权限。运行页显示状态和次数，展开可见负责人、下一步、下次检查时间以及通知失败原因。

CLI：

```sh
crossagents run "实现并验证需求" --planner boss --continue-run --continuation-attempts 3 --continuation-interval 60
crossagents run show <id>
```

API：`POST /v1/runs` 的 `policy.continuation` 为 `null`/省略时关闭；传入 `{}` 使用默认值，也可明确设置：

```json
{"policy":{"continuation":{"max_attempts":3,"interval_seconds":60}}}
```

`max_attempts=0` 不发送恢复通知；`interval_seconds=0` 按 1 秒处理。hub 每约 5 秒在预算检查成功后核对一次，所以不会保证秒级准时。API 的计划批准请求也可带该策略，其他配置入口保持原有行为。

`GET /v1/runs/{id}` 的 `run.continuation` 保存状态；MCP `whoami` 同时返回当前状态与策略。状态变化发出 `run.continuation_changed`，GUI 据此刷新，CLI events 可以查看历史。

## 判定与边界

| 状态 | 行为 |
|---|---|
| 已结束、取消或失败 | 不再唤醒 |
| 人工/预算暂停 | 不再唤醒，保留暂停原因 |
| 等待计划批准、存在本 run 的未回答人工问题/操作审批 | 等待人或原有超时机制；不代答 |
| 主管有正在执行的轮次或排队消息 | 等待，不追加恢复通知 |
| 未结束任务的 worker/reviewer 有轮次或排队消息 | 等待任务及其依赖；长时间无输出也不视为停滞 |
| 任务正在验证 | 等待检查 |
| 没有执行者，任务停滞、待审查、等待主管回答、依赖无法继续等 | 延时唤醒主管，要求先核对现场，再决定补报、回答、返工或改派 |
| 所有子任务结束 | 延时提醒主管对照原需求、失败/取消任务及集成检查完成验收；不自动认定成功 |
| 没有子任务，主管空闲 | 提醒主管继续在 run 分支实现或验证收尾，覆盖直接由主管开发的 Work |

当前选择保守等待：一个任务仍在执行，或本 run 尚有一个人工问题时，不自动催促主管处理其他停滞任务。已有的普通任务事件仍然照常通知发起人。这一版不对运行中的模型或验证命令做超时杀进程，也不自动重放工具调用。

## 持久化和次数

状态保存在原有 SQLite run JSON 中，不需要数据库迁移。缺失字段读作关闭/无检查点。检查点包括负责人、阶段、下一步、累计次数、上次尝试及下次到期时间、投递错误。

每次先在 run 锁内持久化扣除额度，再通过已有的通知摘要投递，既不打断当前轮次，也不另建并发会话。任务变化、取得进展及 hub 重启都不重置额度。恢复期间先按当前任务和运行时状态核对现场，正在接管的 worker 不会因重启被当成需要重放的任务。开启此策略后，重启时原有的恢复提醒交给持久化时钟统一处理，避免绕过次数上限。

这里采用保守的“先记账再投递”：若在两者之间崩溃，或投递失败，会消耗一次额度；重启不会立即重发这一次，之后仍可在间隔到期后使用剩余额度。这不是事务型消息 outbox，不能保证每次预留都必达。失败原因可查看；次数用完显示「需要人工处理」，停止自动唤醒。用户仍可直接给主管发指示，原有交互和任务工具照常可用。

预算先于恢复检查，预算读取失败时本轮不恢复。开启持续推进的 run 在 Planning 阶段也结算预算，覆盖未拆任务的主管开发。预算暂停、计划审批、人工问答、run checks 和落地权限仍由原机制强制执行。

## 验证

`crates/mock-agent/tests/continuation.rs` 使用真实 hub、SQLite 和脚本化 agent 验证停滞恢复、并发核对不重复预留、正常等待、排队消息、人工等待、预算暂停、次数耗尽、实际 hub 重启后的计数与到期时间、子任务结束后的验收提醒、默认关闭兼容性。mock 不衡量真实模型能否正确选择修复策略；模型质量与真实用户需求的最终验收仍需实际使用验证。
