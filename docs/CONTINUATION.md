# 可选的运行持续推进

持续推进为没有正常执行者的 Work 提供有限次数的主管唤醒。默认关闭；旧配置、旧数据以及普通任务通知继续按 H1 工作。它不判断代码是否正确，不替 agent 接受任务，也不自动批准计划或落地。

## 开启与查看

GUI：首页创建 Work → 更多选项 →「停滞时唤醒主管」，设置整个 Work 的最多唤醒次数和等待间隔。默认值为 3 次、60 秒；选择全托管本身不会开启此功能，也不会改变落地权限。

运行页的「持续推进」一栏既显示状态（阶段、已唤醒次数/上限，展开后是负责人、下一步、下次检查时间、通知未送达原因），也是**改策略的入口**：开/关、最多唤醒次数、等待间隔、无进展多久上报，以及「重新加额度」。次数耗尽时这一栏默认展开并标红、「重新加额度」变成主按钮——那正是人打开这个页面的时候。没有可加额度的记录（已关闭）时按钮禁用并说明原因；数字填错时保存禁用并点名哪个字段；请求被拒会显示 hub 的原话，403 另附一句需要 write 权限。

CLI：

```sh
# 建 Work 时开启
crossagents run "实现并验证需求" --planner boss --continue-run --continuation-attempts 3 --continuation-interval 60
crossagents run show <id>

# 改一个已经开着的 run：上限、间隔、无进展上报，以及重新加额度
crossagents run policy <run> --continue-run --attempts 5 --interval 120 --stuck-minutes 15
crossagents run policy <run> --continue-run --reset
crossagents run policy <run> --continue-run --no-stuck
crossagents run policy <run> --no-continue
```

API：`POST /v1/runs` 的 `policy.continuation` 为 `null`/省略时关闭；传入 `{}` 使用默认值，也可明确设置：

```json
{"policy":{"continuation":{"max_attempts":3,"interval_seconds":60,"stuck_minutes":null}}}
```

已经开着的 run 由**人**通过 `POST /v1/runs/{key}/policy` 改（鉴权级别与「人落地一个 run」同级，agent 没有对应的 MCP 工具，主管改不了自己的额度）：

```json
{"continuation":{"enabled":true,"max_attempts":5,"interval_seconds":120,"stuck_minutes":15},"reset_attempts":true}
```

`continuation` 整个省略 = 策略不动；`{"enabled":false}` = 关掉，`policy.continuation` 与 `run.continuation` 一并清空，时钟之后直接跳过这个 run。`enabled:true` 时省略某个限额 = 保留 run 原值（原本没有策略就用默认 3 / 60）。`stuck_minutes` 是三态：不写 = 保持原值，数字 = 设定，`null` = 关掉无进展上报。`reset_attempts:true` 把已唤醒次数归零、清掉「耗尽已通知」标记，用来重新武装一个已经耗尽的 run——**这是人的操作，额度不会因为有进展自动回补**。响应是 `RunDetail`；空请求（既不改策略也不归零）返回 400。关掉时不会发 `run.continuation_changed`（那个事件必须带一个状态，而状态已被清空），客户端以这条路由的响应为准刷新。

`max_attempts=0` 不发送恢复通知（视为一上来就用尽，仍会有下面那条耗尽的 Notice）；`interval_seconds=0` 按 1 秒处理。hub 每约 5 秒在预算检查成功后核对一次，所以不会保证秒级准时。API 的计划批准请求也可带该策略，其他配置入口保持原有行为。

`GET /v1/runs/{id}` 的 `run.continuation` 保存状态；MCP `whoami` 同时返回当前状态与策略。状态变化发出 `run.continuation_changed`，GUI 据此刷新，CLI events 可以查看历史。

## 判定与边界

| 状态 | 行为 |
|---|---|
| 已结束、取消或失败 | 不再唤醒 |
| 人工/预算暂停 | 不再唤醒，保留暂停原因 |
| 等待计划批准、存在本 run 的未回答人工问题/操作审批 | 等待人或原有超时机制；不代答 |
| 主管有正在执行的轮次或排队消息 | 等待，不追加恢复通知 |
| 未结束任务的 worker/reviewer 有轮次或排队消息 | 等待任务及其依赖；长时间无输出也不视为停滞 |
| 任务正在验证 | 等待检查 |
| 以上三种「有人在忙所以等着」的状态，且开了 `stuck_minutes`，而 run 自己的持久化事实已连续这么多分钟没有变化 | 按同一份额度和间隔唤醒主管，提示里点名是哪个 agent / 哪个任务、安静了多久，由主管自己决定中断、改派还是继续等。**不杀进程、不打断轮次、不重放工具调用**；阶段仍显示为原来那个等待阶段 |
| 没有执行者，任务停滞、待审查、等待主管回答、依赖无法继续等 | 延时唤醒主管，要求先核对现场，再决定补报、回答、返工或改派 |
| 所有子任务结束 | 延时提醒主管对照原需求、失败/取消任务及集成检查完成验收；不自动认定成功 |
| 没有子任务，主管空闲 | 提醒主管继续在 run 分支实现或验证收尾，覆盖直接由主管开发的 Work |

当前选择保守等待：一个任务仍在执行，或本 run 尚有一个人工问题时，不自动催促主管处理其他停滞任务。已有的普通任务事件仍然照常通知发起人。无论是否开启 `stuck_minutes`，这一版都不对运行中的模型或验证命令做超时杀进程，也不自动重放工具调用——超时只是**上报**。

`stuck_minutes` 判定「有进展」只认 hub 已经持久化的事实：run 或任一 task 的 `updated_at` 变新（所有任务变更都走 `store_task`/`transition`，run 变更走 `set_run_status`/landing），或该 run 自己的 agent（主管 + 各任务 assignee/reviewer）在上次书签之后追加过事件（回合开始、输出、工具调用、消息）。书签在第一次进入该等待阶段时以当时为起点，不拿更早的记录冒充进展；**沉默本身不算卡死**。反过来说，一个回合卡在单条很慢的命令里（长编译、长 fetch、模型还没吐出第一个 token）既不写记录也不发事件，超过阈值就会被上报一次——这正是它默认关闭、以分钟计、且只上报不打断的原因。判据是 run 级的：只要该 run 任一任务在动，另一个真卡住的 agent 也不会被上报。

## 持久化和次数

状态保存在原有 SQLite run JSON 中，不需要数据库迁移。缺失字段读作关闭/无检查点。检查点包括负责人、阶段、下一步、累计次数、上次尝试及下次到期时间、投递错误，“耗尽是否已通知”“投递失败是否已通知”两个标记，以及开了 `stuck_minutes` 时的无进展书签 `stuck_watch`（上次看到进展的时间 + 事件日志读到的序号）。书签同样持久化，所以 hub 重启后接着算同一段安静期而不是从头再等；超时上报之后书签挪到当时，下一次要再等满一个 `stuck_minutes`。

每次先在 run 锁内持久化扣除额度，再通过已有的通知摘要投递，既不打断当前轮次，也不另建并发会话。任务变化、取得进展及 hub 重启都不重置额度。恢复期间先按当前任务和运行时状态核对现场，正在接管的 worker 不会因重启被当成需要重放的任务。开启此策略后，重启时原有的恢复提醒交给持久化时钟统一处理，避免绕过次数上限。

这里采用保守的“先记账再投递”：若在两者之间崩溃，或投递失败，会消耗一次额度；重启不会立即重发这一次，之后仍可在间隔到期后使用剩余额度。这不是事务型消息 outbox，不能保证每次预留都必达。失败原因可查看；次数用完显示「需要人工处理」，停止自动唤醒。用户仍可直接给主管发指示，原有交互和任务工具照常可用。

次数用完时，hub 通过既有的人工待办建一条 Notice（不需要打开 run 页）：写明是哪个 run、当时停在什么阶段（耗尽前实际等待的阶段）、已唤醒几次/上限几次，以及检查点里建议的下一步。同一个 run 只通知一次：是否已通知记在 run JSON 的 `exhausted_notified` 里，每约 5 秒的核对和重启后从 run JSON 读回的检查点看到的是同一个持久化标记，所以既不会因为反复核对重发，也不会因为 hub 重启重发。投递失败同样会留一条 Notice，按同一规则连续失败只通知一次；投递恢复成功后标记清除，此后再失败会重新通知一次。人重新武装这个 run（把 `attempts` 归零，或调高上限让它重新低于上限）时标记一并清除（见 `crates/orchestrator/src/continuation.rs`），因此下一次耗尽会再通知一次。与额度一样，标记在通知之前先持久化：崩溃可能丢掉这一条 Notice，但不会重复发送。未开启此策略（`policy.continuation` 为 `null`/省略）的 run 不写检查点，也不产生这些 Notice。

预算先于恢复检查，预算读取失败时本轮不恢复。开启持续推进的 run 在 Planning 阶段也结算预算，覆盖未拆任务的主管开发。预算暂停、计划审批、人工问答、run checks 和落地权限仍由原机制强制执行。

## 验证

`crates/mock-agent/tests/continuation.rs` 使用真实 hub、SQLite 和脚本化 agent 验证停滞恢复、并发核对不重复预留、正常等待、排队消息、人工等待、预算暂停、次数耗尽、实际 hub 重启后的计数与到期时间、子任务结束后的验收提醒、默认关闭兼容性，以及次数耗尽的通知：耗尽时恰好一条 Notice（内容含 run、阶段、次数和下一步）、多轮核对和真实重启都不重发、重新武装后允许再通知一次、次数上限为 0 时只通知一次、未开启策略的 run 不产生该 Notice。同一文件还验证了无进展超时：`stuck_minutes` 为空时一直忙着也永不上报（行为与加这个字段之前一致）、安静的 worker 被上报且提示里点名 agent 与任务、阈值内任务动过或 agent 有新事件都不上报、主管自己的回合挂住时点名主管且 agent 仍是 Running（没被打断）、超时上报与普通唤醒共用额度且只发一条耗尽通知。

`crates/mock-agent/tests/run_policy.rs` 验证人改策略这条路由：耗尽后重新武装能继续被唤醒且再耗尽会再通知、关掉后不再唤醒且不留状态、运行中的 run 可以中途开启、只读凭据 403 无凭据 401 且 run 不变、改上限不影响其余策略、低于上限也能归零、空请求 400，以及 `stuck_minutes` 的三态（设定 / 不写保持原值 / `null` 关掉）。GUI 侧 `apps/gui/src/lib/continuation.test.ts` 用纯函数验证表单初值、数字校验、开关各自发什么请求体、空的无进展字段发 `null`、非法字段点名、归零只发 `reset_attempts`、403 保留后端原话。

mock 不衡量真实模型能否正确选择修复策略；模型质量与真实用户需求的最终验收仍需实际使用验证。两处仍未覆盖：投递失败那条 Notice 只有实现和代码审查，没有集成测试（真实 hub 下很难让投递稳定失败，需要一个可注入失败的 Host 替身）；GUI 的保存/归零没有真起 hub 点过一遍，只有类型、mock 预览和纯逻辑测试。
