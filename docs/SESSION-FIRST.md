# CrossAgents：会话为主的最小改造

> 版本：v1（评审收敛版）· 2026-10-31  
> 基线：0.1.19。状态：核心 v1 与 §7 聊天精简均已在 main 实现，尚未发布。  
> 核心范围：独立 lead、`Run.origin_chat_id`、侧边栏父子结构，以及静默结束摘要。

## 1. 本版决策

用户和父 session 正常聊天；需要独立工作的事项通过 `work_start` 发起 run。run 使用新的 lead，必要时由 lead 调用 `plan_submit`，hub 按现有规则派发执行 session。

本版完成下面四项改动：

1. **从聊天发起 run 时，始终使用独立 lead。** 复用已有 `fresh: true` 路径，父 session 保留在原目录。
2. **run 保存来源对话。** 新增 `origin_chat_id`，与 run 一起保存、发布并返回 API。
3. **侧边栏按来源嵌套。** 显示“对话 → run → 成员”；无来源或无法显示来源的 run 仍有独立入口。
4. **结束结果静默留给父对话。** 不唤醒父模型，等下一次消息再带入一行摘要。

普通聊天的说明与工具精简可以单独提交，不阻塞上述改动。

继续遵循“hub 服务模型”的原则：模型决定直接完成、招募帮手或提交任务。已有预算、并发、权限与用户设置继续生效；本方案不新增“先勾选允许协作”、父对话活动 run 数上限或更小的帮手数量上限。

## 2. 产品行为

```text
对话
└ CrossAgents 方案讨论 · Suki
  ├ 每轮消耗统计           run · 进行中
  │ ├ Nova                主导
  │ ├ Zeno                用量采集
  │ └ Jasper              界面展示
  └ 工具说明精简           run · 已完成

项目中的独立工作
└ 修复构建问题             run · 从 Home 发起
```

- 小任务在当前 session 直接做，不强制经过父子交接，也不新增任务大小分类模型。
- 父 session 可以继续聊天，也可以再发起其他 run；它不因自己发起的 run 被 claim。
- run lead 可以自己完成工作，不要求先提交计划或提前启动 worker。
- 需要分工时，由 run lead 调用 `plan_submit`。计划创建的是 Task，hub 再安排执行 session；Task 与 session 不要求一对一。
- `work_start` 仍使用现有的提议、开始/不用卡片和启动通知。v1 不增加新的聊天内结果卡片或父模型监督循环；结束结果通过静默提示补入下一次消息。
- 从 Home 发起的 run、旧 run 和无来源 run 继续独立显示。

Session 指 CrossAgents 的稳定 `AgentId`，父子关系不绑定厂商原生 session ID。

## 3. 保留 0.1.19 的自动策略

**聊天中提议的 Work 经用户开始后，默认自动批准计划、自动落地。** 独立 lead 接手这些权限，本次改造不把它们改回人工审批。

| 项目 | 本版行为 |
|---|---|
| `policy.plan_approval` | 保持 `PlanApproval::Auto` |
| `policy.land` | 保持 `LandPolicy::Auto` |
| `policy.spawn` | 沿用当前默认 `true` 及已有用户策略 |
| `policy.delegate`、模型限制、预算、并发、重试 | 沿用现有设置和语义 |
| 父聊天中的招募与消息能力 | 保留，模型可按需要使用 |
| lead 的模型、账号、思考强度和人设 | 复用已有复制配置的行为，不自动降级或升级模型 |

`RunConfig.auto_approve` 是旧兼容字段；不要只看它当前为 `false` 就推断计划需要人工批准。有效行为还取决于 `policy.plan_approval`。

自动落地继续经过已有的检查、冲突处理和操作权限机制。Home 的独立 run 按原入口的策略创建，不统一改成聊天路径的默认值。

## 4. 后端最小改动

### 4.1 强制使用已有的独立 lead 路径

在 `work_decided` 的开始分支，将现有调用改为：

```rust
self.create_run_with_choice(new, Some(true), false).await?
```

其中 `new` 使用现有 brief、工作区、模板和 `RunConfig`；只附加来源对话信息。核心行为切换就是复用现有的 `copy_lead`，不新建一套 session 管理逻辑。

新 lead 使用独立 `AgentId` 和执行目录。父 session 的 `home`、`cwd`、原生会话及历史保持原状；不要再以 `move_cwd` 能力判断是否借用父会话。

复制完成后确认 `run.planner != run.origin_chat_id`。现有复制、claim、创建失败清理、保留工作区与结束逻辑继续使用。

### 4.2 新增来源字段

在 `Run` 增加：

```rust
#[serde(default)]
pub origin_chat_id: Option<AgentId>,
```

在内部创建参数 `NewRun` 增加对应字段：

- `work_decided` 设置为 `Some(proposer)`，来源由现有 `HumanItem.from` 确定。
- 其他入口默认传 `None`，本版不增加来源编辑接口。
- `engine.rs` 在构造 Run 时写入；字段必须在首次保存、`RunCreated` 和 kickoff 前就存在。
- 不采用“先创建 run，再在 work.rs 更新来源”的方式，避免首次 API/事件缺少关系。
- 若内部调用同时带来源并要求原会话本人作为 lead，明确拒绝这个矛盾请求。

`ListRunsResponse` 和 `RunDetail` 已直接包含 `Run`，更新共享类型和 GUI bindings 后即可返回来源；不需要新增 run 查询或控制 API。

### 4.3 存储兼容，无需迁移

目前 Run 已整体序列化在 `runs.data` 中。来源字段继续随 JSON 保存；旧数据缺少字段时，`#[serde(default)]` 将其读取为 `None`。

`list_runs` 已加载全部记录，侧边栏在客户端分组，没有按来源执行 SQL 查询的入口。因此 v1 不增加索引或迁移文件，也不批量改写历史 JSON。

现有 `work_id`、Work 数据实体及“同 Work 同时一个未结束 run”的约束保持原意。来源聊天与 Work 分组是两种关系。

### 4.4 两处必要的配套

**防止子 run 把父会话借回来。** 在现有执行会话借用/占用检查处，拒绝 `agent.id == run.origin_chat_id` 的本人执行请求。该检查覆盖 worker、reviewer 和重派路径；父会话仍可用作新执行者的配置模板。无需新增 SessionPurpose 类型或重写旧会话复用体系。

**保留未落地提示。** 当前 `unlanded_home_of` 通过 `run.planner == caller.id` 查找之前的工作。使用独立 lead 后，父聊天应能通过 `origin_chat_id` 找到自己发起的上一项工作；保留旧 planner 匹配作兼容，并继续限定仓库和最近一次执行的原有语义。

这两处都围绕现有代码补检查/查询，避免关系切换带来行为回退。

### 4.5 实现中补上的两条

**只由对话发起 Work。** `work_start` 仍只开放给 Conversation 组。子 run 的 lead 带 `spawned_by_run`，不属于该组，看不到这个工具；下一项工作由来源聊天发起，`unlanded_home_of` 通过 `origin_chat_id` 找到上一项未落地的工作。这样不会出现由 lead 再发起、挂不到任何聊天下的 run 链，也不给每个 lead 多加一个工具。

**lead 自己做完的 run 可以先落地。** lead 不交计划、自己完成时，run 一直停在 `Planning`。原来 `run_land` 只接受 Running / Completed / Failed，这类 run 的落地一律被拒；现在 `Planning` 也可落地（空分支仍拒绝），lead 可以先 `run_land` 再 `run_finish`。

## 5. 侧边栏最小改动

### 5.1 建树规则

从已加载的 run 和 agent 数据派生，不增加新的持久树结构：

1. 按 `origin_chat_id` 将子 run 分组。
2. 父对话可显示时，将子 run 渲染在它下面，复用现有 `RunRow` 和成员渲染。
3. 普通独立 run 列表排除已嵌套的 run。
4. `origin_chat_id` 为空、父对话不存在或已归档而无法显示时，run 回到所属项目的独立列表，不能消失。
5. 按全局 ID 关联来源，不只检查当前项目分组：父对话与 run 可能原本显示在不同分组。

父对话不得仅因它是配置模板或来源，就被 `inRuns` 过滤掉。执行成员仍按实际 `run.planner`、task assignee/reviewer 等现有关系显示；来源不是执行成员。

### 5.2 保留现有操作

- 对话、run、成员保持现有路由和身份，点击 run 仍进入现有 run 页面。
- 复用当前折叠与成员展示机制，不重写 run 页面。
- 搜索命中子 run 或成员时，保留并展开父路径，不能先把父行过滤掉。
- 选中子 run/成员时，“更多”截断不能隐藏整条父路径。
- 置顶沿用现有入口，指向同一对象；普通列表只保留一个规范位置。
- 删除或清理 run 不删除来源对话。归档父对话后，子 run 仍可在项目中找到。

v1 不为旧 run 回填来源，不根据标题或名字猜测关系；旧聊天已经与 lead 是同一个 session 的记录继续按旧结构显示。

## 6. 上下文与消耗

### 6.1 使用现有 brief

新 lead 使用 `work_start.request` 对应的 brief，沿用现有 `brief_of` / kickoff 路径。父模型写 brief 时提供目标、已定决策、约束、相关路径和完成条件即可。

不引入新交接格式、自动压缩或历史分叉。也不为每次开始工作另调一个模型生成结构化摘要。

本版的节省来自：执行历史留在独立 lead，父聊天不再因为亲自执行而积累全部代码、日志和返工记录。普通小任务没有新增编排轮次。

### 6.2 静默回传结束结果

run 完成、失败或取消后，hub 为来源对话留下一行结果：标题、run ID、状态、简短 summary/原因，以及已落地还是仍在 run 分支。后续手动落地时更新同一项提示，避免把旧的未落地状态传给父模型。

普通 `deliver` 会启动会话，不适合这条路径。复用 Runtime 已有的 `tell_later` 机制：以 run ID 区分提示，记录时不启动 session、不打断当前轮次、不触发新的模型调用；下一次消息送给父 session 时一起带入，然后消费一次。多项工作的摘要不能相互覆盖。

本版复用现有内存待传提示，不新建持久队列；hub 重启会丢失尚未消费的提示，已保存的 run summary 和详情仍保留。持久化补传按后续实际需要另做。

当前 `work_decided` 的开始/不用通知可能产生一次父模型确认回复，v1 保留这个行为。静默结束摘要本身不产生额外模型轮次。

独立 lead 仍需初始化并可能重读文件，不能承诺所有小任务都更便宜。需要完整历史的复制功能不属于这版。

### 6.3 落地遇到父工作区未提交改动

保留 Auto/Auto。若现有落地检查因主工作区的暂存改动，或与 run 修改重叠的未提交文件而拒绝，lead 应调用 `run_finish`，说明结果仍在 run 分支，留给用户之后落地。

lead 不重复尝试，不替用户 commit、unstage、stash 或丢弃改动，也不换一种命令绕过拒绝。拒绝信息与 lead 说明均写明这条后续行为。`run_finish` 只按原有机制保存 run 工作区自己的结果。

### 6.4 用现有数据比较

先用已有 usage、`cached_input_tokens` 和 `usage_series` 做粗略前后对照，不等待新的用量系统：

- 保持模型、思考强度、任务与仓库状态一致，冷缓存和热缓存分开看。
- 比较输入、缓存输入、输出与耗时；包含父聊天启动通知和子 lead 的实际消耗。
- 重点观察同一聊天执行多项工作后，继续普通聊天的用量。
- 对每次都没有启动 run 的小任务，检查没有新增分类、交接或总结调用。
- 数据只支持会话/轮次粒度时，就按该粒度报告，不补算不存在的请求级精度。

不承诺固定节省百分比，也不把 token 直接换算成订阅额度百分比。

## 7. 普通聊天精简：可单独提交

这一项与父子结构独立，可以一起实现，也可以随后再做。

先处理明确依赖 run/task 的内容：将 task、run workspace、验收等工具从 `ALL` 中移出，按现有角色及实际执行上下文开放。列出工具和调用工具要执行一致的检查；不能只从菜单隐藏。

普通聊天保留身份、队友发现、招募、消息、提问、提醒、经验和笔记等现有能力。不能为了精简工具，把模型自主协作改成默认禁止。

对应说明也按当前是否正在执行任务收敛：普通聊天不带“必须 task_complete”或完整的 run 收尾流程。先复用已有 run/claim 信息，不以新增整套会话用途类型作为前置。

保留原生读写与终端能力，所以聊天中的小改动仍能直接完成。已有用户人设、项目规则和构建约束继续生效。

本版及当前路线不引入 `capability_find/call`；先做直接分组与说明精简，观察实际收益。

**实现情况。** task、worktree、检查、审查、合并相关的 17 个工具从 `ALL` 移到 `RUN` 组（Lead / Assignee / Reviewer）。`groups_of` 看 run 当前是否占用该会话：普通聊天（角色为 worker、没有 claim）只有 Everyone + Conversation，说明只有 COMMON + 构建锁 + 对话说明；被 run 占用时按 claim 的角色给对应组和说明，列出与调用用同一套判断。角色为 planner / reviewer 的旧聊天保持原样：run 可能就地占用它而不重开会话，原生客户端不会重新拉工具清单。一个普通聊天的 hub 工具从 50 个（约 25k 字符定义）降到 29 个（约 16k），说明从约 4.3k 降到约 3.3k 字符。聊天招募的帮手（`spawned_by_agent`）仍按角色拿全套工具，留待之后再看。

## 8. 提交顺序

| 提交 | 范围 | 完成后得到什么 |
|---|---|---|
| 1：后端关系 | fresh lead、来源字段、API/bindings、静默摘要、落地指引和测试 | 原聊天留在原处，子 run 有明确来源 |
| 2：侧边栏 | 来源分组、三层渲染、搜索/选中/回退入口和测试 | 对话 → run → 成员 |
| 3：聊天精简，可独立 | 工具作用域与说明精简 | 普通聊天减少无关编排内容 |

提交 1、2 实际合在一个提交（2c98478）；提交 3 随后单独提交。

**先落地结构，再改进统计。** 用现有数据进行粗略对比可与提交 1、2 并行准备，不作为上线依赖。

现有创建清理、卡片处理锁与重复点击测试继续复用。这版不新增创建事务记录、补偿调度器、持久投递队列、kickoff 协议或重启核对状态。

## 9. 验收

| 场景 | 要验证的结果 |
|---|---|
| 支持移动的原生会话发起 Work | 也生成新 lead；父 ID、原生会话及目录不变 |
| 不能移动的驱动发起 Work | 继续使用现有复制能力，无额外架构要求 |
| API 与首条 RunCreated | 已带正确 `origin_chat_id`，不是事后补写 |
| 重启后重新读取 | 来源仍在；旧记录缺字段时正常读取为 None，无需迁移 |
| run 完成、失败或取消 | 不唤醒父模型，下次消息带入对应结果且只消费一次 |
| 父工作区有阻止落地的未提交改动 | 拒绝提示引导结束，run 可保留分支结束；用户工作区与索引不变 |
| 同一聊天再发起另一项工作 | 来源相同、lead 不同，不因父聊天被占用而拒绝 |
| lead 独立做完或 plan_submit 分工 | 两条现有执行路径都正常，不强制拆任务 |
| 协作、自动批准和落地 | 模型仍可按需招募；Auto/Auto 不回退 |
| task 试图 fresh:false 借父聊天 | 被局部占用检查拒绝，使用克隆模板仍可行 |
| 新工作前有未落地的来源工作 | 原有提示仍可查到正确工作 |
| 搜索/选中子 run 或成员 | 父路径可见，点击路由不变 |
| 无来源、旧 run、Home run | 仍独立显示；不推断历史来源 |
| 来源归档或不存在 | 子 run 保留独立入口 |
| 删除子 run | 父对话及历史不被删除 |
| 小任务直接完成 | 不新增 run、分类模型或摘要轮次 |
| 工具精简（若本次包含） | run/task 工具正确分组，招募与消息能力可用 |

**目前的测试覆盖。** 已有测试：独立 lead 与父会话保留、同一聊天再发起（含子 run 打开时）、lead 无 `work_start`、静默结束摘要、借用父聊天被拒、父工作区未提交改动时结束在分支、无计划 run 先落地、未落地提示、来源字段 round trip 与旧 JSON 读取、侧边栏建树（`sidebarTree.test.ts`）。尚未有测试：首条 `RunCreated` 事件即带来源（现有测试经 API 事后读取）、跨 hub 重启的端到端读取、删除子 run 不删父对话、侧边栏搜索/选中/“更多”截断时父路径可见（建树测试只覆盖分组函数）。

优先更新已有 `work_start` 测试，尤其是原来断言“可移动的提议者亲自领导”的测试；它现在应验证独立 lead 和父会话保留。

保留并复跑重复开始、开始/关闭卡片竞争、计划执行、落地和会话复用的相关测试；新增来源字段 round trip、旧数据读取及侧边栏建树测试。功能实现时按仓库规则跑相关检查。

## 10. 后续事项，不阻塞 v1

按后续实际使用需要再安排：

1. 聊天内 run 状态/结果卡片，尽量用程序呈现，减少无意义确认与复述。
2. 父对话对 run 的查询、补充和停止交互；先看现有入口是否足够，再决定是否增加工具。
3. 更细的父子用量归因，以及必要的计数恢复、去重改进。
4. 有明确故障证据后，针对性加强创建与投递可靠性。

它们不作为“会话 → run → 成员”上线的依赖，也不预先搭建通用能力分发器或完整消息系统。
