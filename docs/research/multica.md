# Multica：可借鉴的设计

> 2026-10-26 调研。读的是官网、GitHub README 和中文文档（核心概念、工作方式、任务唤醒、小队、运行、守护进程与运行时、安装 AI 编程工具、工作流、自动化）。没有实际部署试用。
> 同系列：[magpie 与 Lancer](magpie-lancer.md)。

## 1. 它是什么

[Multica](https://multica.ai/)（[GitHub](https://github.com/multica-ai/multica)，source-available）把编程 agent 当成团队成员：给它分配 issue，它领取、在评论里汇报、遇阻主动报告，做完交回审核。

| | Multica | CrossAgents |
|---|---|---|
| 结构 | 服务端 + 每台机器一个守护进程；守护进程扫描本机 CLI，每款注册成一个运行时 | hub + 节点（MULTI-NODE），驱动按描述文件找 CLI |
| 主界面 | 任务看板，agent 在评论里说话 | ChatGPT 式对话，Chat / Work |
| agent | 一份配置（指令、模型、skill、运行时），只在被触发时执行 | 会话即 Worker，空闲挂起、来消息恢复 |
| 接 CLI | 27 款，统一调用；不替用户装 CLI | 三家原生驱动 + ACP 兜底；描述文件声明安装方式 |

结构几乎一样，形态不同。界面不学，学它在调度规则上踩过的坑。

## 2. 建议做的（按优先级）

### P0：什么时候把谁叫醒

这三条合起来，就是我们「agent 间通信」里还空着的那一块。都是机械规则，hub 按条件检查，不违反「hub 不思考」。

1. **唤醒规则**（[任务唤醒](https://multica.ai/docs/zh/issue-wakeups)）。agent 做到一半要等（子任务、人回复、CI、某个时间），在运行中给自己挂一条规则，然后结束本次运行，等待期间不占进程。条件满足后起一次普通运行，并告诉它是被什么唤醒的。
   - 条件：某时刻、定期检查（必须有截止日）、有人回复（可限定是谁）、字段变成某值、某 agent 的运行结束、子任务完成、关联 PR 的 CI 结束、其他任务状态变化。
   - 防失控，可直接抄：agent 自己的消息和改动不唤醒自己；同一 agent 已有排队中的运行时，新唤醒并入那一条；唤醒链第三次经过同一规则且中间没有人参与，或 1 小时内触发超过 12 次，自动暂停；等待类默认最多 7 天，超时也唤醒一次，并告诉它「要等的事没发生」；定期检查没事可报时可以静默结束，时间线里合并成一条。
   - 任务完成或取消时，上面的唤醒全部关闭，没开始的运行撤回。
2. **子任务分阶段，结束时唤醒父任务负责人**。子任务带 stage；一个阶段全部结束就唤醒父任务负责人（agent 唤醒它，小队唤醒队长，人则发通知），由它检查依赖、放行下一阶段；全部结束再唤醒一次做汇总。这是系统内置规则，不用手动建。对应 Work：lead 拆任务，一批做完自动叫 lead 回来。
3. **队长的唤醒表**（[小队](https://multica.ai/docs/zh/squads)）。
   - 队长只派活：@ 成员后立刻停，自己不动手；每次评估留一行记录。
   - 唤醒队长：成员发进展但没 @ 任何人时唤醒；显式 @ 了别人不唤醒（已经是明确交接，再叫队长只会空转）；队长自己的消息不唤醒自己；排队去重。
   - 派活协议和花名册是系统追加在队长指令后面的固定段落，用户改不了。
   - 这套直接用来写 Planner 的投递规则（DESIGN §4.5、§6）。

### P1：运行与失败

4. **运行和任务分开**（[运行](https://multica.ai/docs/zh/tasks)）。一次运行结束 ≠ 任务完成，任务状态由负责人推进。
5. **失败原因分两类，只重试基础设施故障**。平台侧（运行时离线、超时、目录准备失败、网络中断）自动重试，默认最多 2 次，网络中断 3 次；`agent_error.*`（鉴权、额度、模型）重试无用，直接停并说明原因。重试时会话安全就续原会话；上下文溢出这类会污染会话的，在原目录开新会话。
6. **本地目录锁**。同一工作目录同时只跑一个运行，后来的进入 `waiting_local_directory`，界面上能看到在等什么。我们允许多个 Worker 共用目录（如 run 的集成目录）时需要同样的状态。

### P1：多节点（MULTI-NODE 直接参考）

7. **心跳与离线判定**（[守护进程与运行时](https://multica.ai/docs/zh/daemon-runtimes)）。心跳 15 秒一次，约 3 分钟判离线；离线时排队的运行不转到别的机器。
8. **排队超时要两个条件同时满足**：运行时心跳缺席超过宽限期（默认 3 小时），且这条运行自己也排了这么久。指派给一台正在休眠的机器时，有完整一个宽限期把它叫醒。

### P2：CLI 接入（补进描述文件）

9. **最低版本**（[安装 AI 编程工具](https://multica.ai/docs/zh/install-agent-runtime)）。低于最低版本不注册（Claude Code 2.0.0、Codex 0.100.0 等）。描述文件加 `min_version`，GUI 显示「版本过低」，不提供模型。
10. **MCP 合并**。agent 带 MCP 时，每次运行生成一份专用配置（Claude 用严格模式），同时读该 CLI 用户级的 MCP 配置合并进去，否则用户自己配的 MCP 失效；CodeBuddy 会自己加载用户配置，就不预先合并，免得同一服务器起两次。要核对我们给 Claude（`--strict-mcp-config`）和 CodeBuddy 注入 hub MCP 时有没有这两个问题。
11. 「终端找得到、守护进程找不到，通常是 PATH 不同」——它只能让用户重启守护进程；我们读注册表 PATH（提交 9971310）已经解决，方向是对的。逐家的绝对路径覆盖（`MULTICA_<PROVIDER>_PATH`）我们已有 `[locate] env`。

### P2：以后

12. **工作流交接**（[工作流](https://multica.ai/docs/zh/workflows)）。每一步设「交给谁、完成后进入哪一步、打回时退回哪一步」，交接前能预览 agent 会收到的说明；交接时默认停掉上一位还在跑的 agent。适合 Work 的 lead → worker → reviewer 流转。
13. **费用**。执行日志里每次运行一根费用条，按 agent、模型拆分。与 magpie 的额度管理一起做。
14. **自动化熔断**（[自动化](https://multica.ai/docs/zh/autopilots)）。7 天内至少 50 次运行且失败率达到 90%，自动暂停并通知创建者。

## 3. 不学的

- 以看板和 issue 为主界面：我们是对话形态，issue 只当内部的任务记录。
- 工作区、成员角色等多租户功能，以及 `custom_env` 存在服务端：我们是个人多机，凭据留在节点。
- 一口气接 27 款工具：三家原生 + ACP 兜底的路线不变。
- 不替用户装 CLI：我们已经做了安装按钮，这是差异点。

## 4. 建议顺序

交接卡（magpie-lancer §2 P0）之后、多节点之前，做 P0 的三条：唤醒规则、分阶段唤醒、Planner 唤醒表。P1 的心跳与排队超时在做 MULTI-NODE B1 时一并落地。
