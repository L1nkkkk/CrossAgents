# CrossAgents：平等 Agent 与项目侧栏设计

> 日期：2026-11-01 · 状态：§7 的 A–D 四个阶段已实现（见 §7 的实施记录）。§6 的 role 字段迁移仍未做。  
> 依据：本次讨论与第二版交互概念图；Cutex desktop 0.2.0（`6216e67`，2026-10-29）的设计文档和源码。  
> 本文替代 [SESSION-FIRST.md](SESSION-FIRST.md) §1 第 3 项、§2 的侧栏示意和 §5 的父子导航树方案；保留它的来源关系、独立 lead、执行隔离、静默回传及自动策略。  
> [DESIGN.md](DESIGN.md) 中 Planner / Worker / Reviewer 的固定身份表述，以本文的任务职责模型为准。旧字段的兼容迁移另行实施。

## 1. 要解决的问题

现在侧栏把对话、run、工作组和成员混在一棵树里。用户看到「G1-3 → Iris 主导」，需要先理解内部执行结构，才能找到想继续聊的对象。上方对话与项目中的工作也容易形成两套入口。

后端的角色标签又把分工变成了资格限制：名为 planner 的聊天会话，曾经不能被指派实现或评审。用户实际需要的是和 Leo 讨论、让 Leo 实现，也让 Leo 检查其他人的工作。

本次设计确立三条规则：

1. **Agent 是平等的协作者。** 模型、上下文和可用状态可以不同，没有由 planner / worker / reviewer 决定的固定权限等级。
2. **职责属于具体工作。** 谁协调、谁实现、谁评审，在 run / plan / task 中表达。
3. **侧栏负责找人和找到待办。** 项目页负责看目标、计划和结果；执行关系不再决定导航缩进。

## 2. 领域模型与边界

| 概念 | 保存什么 | 不承担什么 |
|---|---|---|
| 项目 / 工作区 | 现有仓库归属、成员与工作入口 | 不新增一套与现有 Workspace 平行的项目实体 |
| Agent / session | 稳定 ID、名字、模型配置、会话上下文、运行状态 | 不以固定角色限制可接职责 |
| Work / Run | 一项工作的执行、来源会话、本次协调者、生命周期 | 不作为成员的永久父级 |
| Plan / Task | 目标、依赖、负责人、评审者、完成条件 | 不把负责人转换成永久 worker |
| 待处理事项 | 需要用户回答、确认或恢复的具体事件 | 不复制 Agent，也不是新的会话 |

沿用现有稳定 AgentId，不为这次界面改造拆出独立的「人格」「联系人」「聊天」三套 ID。用户点击 Leo，进入这个 ID 对应的已有会话。

同一个 Agent 可以在任务 A 实现、任务 B 评审；是否能同时执行由现有占用和并发规则决定。平等不等于取消资源隔离或所有 Agent 都具有相同运行时能力。

### 2.1 资格检查

**已实现（0.1.24，`6a247b2`）：** `plan_submit` / `task_create` 指派、`task_assign` 重派、`review_request` 和审批接口的 `assignees` 不再按角色标签拒绝；能否接手只看原有约束（同一工作区、占用、归档与恢复、来源对话保护、驱动能否换目录）。fresh 时任何会话都可作为配置模板。回归测试：`crates/mock-agent/tests/pipeline.rs` 的 `chat_sessions_can_take_tasks_and_review`。

**随后补齐：** run 的显式 `team` 可以写任何会话（不再报「is a planner」）；kickoff 的成员表合成一张「team」，不按 workers / reviewers 分组，「没有默认 worker」按是否在团队里判断；工作区会话一节说明任何会话都能被点名为负责人或评审者。界面上审批卡片的「队友」列出团队和本工作区未归档的会话（除本 run 的主导和来源对话），首页的默认 worker / 升级 / reviewer 三个下拉框也不再按角色筛选。同一测试覆盖 kickoff 的成员表。

**有意保留：**

- 不指定 `team` 时，自动组队仍只收 worker / reviewer 会话：聊天会话可能很多，它们已在 kickoff 的工作区会话一节列出（有条数上限），主导可以点名任何一个。
- `agent_spawn` / 招募拒绝 `role: planner`（`team.rs`）。这是创建默认值，随 §6 的 role 字段迁移一起处理。

本次协调者是 run 内的关系。只有该 run 的协调者才能执行某些控制操作时，依据实际关系校验；不把协调权限扩大为某类 Agent 的永久特权。现有工具作用域限制不随侧栏改造自动取消。

需要独立评审的工作，应依据实际执行者与评审者关系判断，不依据角色标签。这是职责模型的验收要求；实现时应核对已有策略，不能宣称当前已经全覆盖。

### 2.2 本人执行与新建执行会话

必须区分两种操作：

| 方式 | 上下文与身份 | 展示 |
|---|---|---|
| 由已有 Leo 会话执行 | 同一 AgentId，沿用已有会话；通过本人执行资格检查 | Leo · 当前任务名称 |
| 使用 Leo 的配置新建执行会话 | 新 AgentId；复制配置不代表复制历史 | 独立名称；详情注明「使用 Leo 的配置创建」 |

保留现有 fresh 默认值及创建语义，不通过界面暗中改为借用本人。任务详情同时说明配置来源和实际执行者，避免把新会话的活动显示为原 Leo 的活动。

来源会话仍可以作为配置模板，但不能被自己的子 run 借回去执行。新会话收到现有 brief / kickoff 所需背景，不因为这次设计新增一次模型总结或复制全部聊天历史。

## 3. 信息架构

```text
顶栏：应用级入口

侧栏                         内容区
搜索                         点击项目：项目总览
                             计划 / 成员 / 动态 / 结果
需要你 · 2
  Leo   失败重试策略待回答     点击成员：该成员会话
  Iris  测试方案待确认        当前任务、对话、提问与回复

项目                         会话旁工具区（按需打开）
▾ CrossAgents                当前计划 / 改动 / 执行记录
    Iris   补充回归测试
    Leo    实现调度逻辑
    Orion  评审边界条件
▸ CV_Resume

独立会话
  尚未归属项目的会话
```

侧栏只有项目与成员两层业务层级。需要你、置顶和独立会话是分区，不构成身份或执行层级。成员被谁招募、来自哪个 run、用了谁的配置，放在详情和记录里。

run 不再嵌在来源聊天下。项目内全部 run（包括旧记录、无来源记录、来源已归档记录）都能从项目总览找到；工作还未提交 plan 时，也显示工作目标和当前状态，不因没有任务列表而消失。

## 4. 侧栏规则

### 4.1 项目与成员

- 点击项目名称打开项目总览；点击名称旁的箭头只展开或收起成员。
- 点击成员进入该稳定 ID 的会话。成员行不显示「主导 / worker / reviewer」身份标签。
- 第一行：头像、名字、简短状态。第二行：当前任务、最新动作或消息摘要，优先展示有用的工作内容；不拿文件系统路径充当标题。
- 长标题截断并可查看完整内容；不要用 G1-3 等内部编号挤占主标题。编号保留在详情及复制引用中。
- 项目顺序支持持久化；组内置顶优先，其余保持稳定顺序。第一阶段不因流式消息、状态变化或点击选中重新排序，也不自动移动刚变空闲的成员。
- 默认宽度改为概念图选定的 **226px**（现为 264px，`lib/widths.ts` 的 `SIDEBAR.initial`；拖动和按本机保存已有）。文字区域随宽度变化，状态不能挤掉整个名字。
- 有项目归属的普通聊天和执行成员都在所属项目中。无项目归属的会话放在「独立会话」，不再把全部项目聊天重复堆进顶层「对话」。

### 4.2 需要你

- 单独汇总真实待办：待回答问题、有效策略要求的审批、待验收、需要用户处置的失败。不把普通运行、空闲或完成未读全部当作待办。
- 每条显示对象、事项摘要、明确动作（回答 / 查看 / 确认）。点击跳转到实际处理位置，不只打开聊天底部。
- 同一个 Agent 可以有多个事项，按待办 ID 去重，计数按事项计算，不按成员数计算。使用现有持久 ID；确无 ID 时再设计稳定事件键。
- 按进入待处理状态的时间排序，等待较久的在前；流式活动不改变顺序。初始最多显示 3 条，其余从「还有 N 项」展开。
- 事项只有在服务端确认处理完成后移除。仅打开会话不能自动批准、回答或清除真实待办。
- 项目折叠、成员归档或侧栏搜索不能让有效待办消失；跳转目标不可用时明确说明原因。
- 默认展开，有待办才出现；允许收起为计数行并记住选择。底部项目成员仍有唯一的规范位置，这里的重复仅是快捷入口。

### 4.3 状态与未读

| 层次 | 表达 | 例子 |
|---|---|---|
| 需要处理 | 图标 + 文字；有选择地使用强调色 | 有提问、待确认、出错 |
| 正在工作 | 状态点 + 简短动作 | 执行中、评审中 |
| 无需处理 | 弱化文字 | 空闲、离线、已完成 |

「评审中」来自正在执行的任务职责，不是身份。「完成未读」和「需要你处理」分别计数：打开对应内容可清除未读，真实待办仍按处理结果消除。

断连或状态尚未确认时显示「连接中 / 状态未确认」，不能误判为空闲或完成。首期沿用已有活动与未读数据源，避免额外轮询每个会话全文。

### 4.4 搜索、置顶与归档

- 搜索匹配成员名字、话题和当前任务；保留项目标题供定位。搜索期间显示命中成员，退出后恢复原折叠状态，不覆写持久偏好。
- 项目折叠时可以保留选中或待处理标记，不因打开成员强制永久展开全部项目。
- 置顶是指向同一对象的快捷入口，不创建副本；移除置顶不归档对象。
- 已归档成员不挤占日常列表，但项目总览的执行记录、结果和归档入口仍能找到它们。run 结束后自动归档的执行会话也遵循此规则。
- 删除或归档 run 不删除来源对话；归档来源对话不隐藏对应 run。这些生命周期规则继续沿用 SESSION-FIRST。

## 5. 项目总览与会话

项目总览提供计划、成员、动态、结果四个视角。概念图已示意前三项；结果视图属于实现范围，需要补充完成、失败、未落地等样例。

计划按 run / 工作目标组织，展示本次协调者，以及各任务的负责人、评审者、依赖和状态。点击人名打开实际执行会话，点击任务查看规格、交付和执行记录。工作失败或未落地不能被统一显示成「完成」。

成员页查看全部成员及本次分工，支持进入会话；职责不写回永久身份。动态页记录协作事件；结果页保留交付、验证及落地状态，并能返回实际记录。

成员会话顶部显示名字和当前任务。若关联多项工作，明确显示当前任务，并提供关联工作入口，不能任取最近一个 run 作为上下文。

计划、改动和执行记录可以在会话旁按需打开。工具页跟随当前聚焦会话；切换成员不能把另一人的 diff 当成当前人的结果。窄窗口将辅助内容收起为可打开面板，优先保留会话和输入区。首期复用现有并排/工具面板机制，不重写完整布局引擎。

## 6. 不改变的策略与不做的事

- 保留独立 lead、`origin_chat_id`、来源会话保护、静默回传和现有执行隔离。**导航变平不代表执行关系消失。**
- 沿用 SESSION-FIRST 的自动落地及权限配置。**计划审批已于 2026-11-02 改回人工**：从对话发起的 Work 一律 `plan_approval: required`，见 §6.1。概念图中的「方案待确认」不再是特例，而是每次 Work 的常态。
- 每个任务的执行模型由人在计划审批里选：lead 用 `plan_submit` 写清每个 session 要做什么，PlanDock 每行给出队友与「某插件 · 某模型」候选。lead 可以预填 `assignee` 作为建议，但由人最终决定。不新增模型排名、能力评分或自动选型。
- 不直接删除数据库或协议中的旧 role 字段。先停止用它判定职责资格，再检查创建默认值、提示词、工具作用域、配置、存储和旧客户端兼容；迁移另列任务。
- 不照搬 Cutex 的 Director / Operator 固定角色、头饰、桌面托盘、任意拖拽工作区、多窗口及大量外观开关。
- 不新增模型判断任务大小、Agent 能力排名或角色评分。

### 6.1 计划审批改回人工（2026-11-02）

**起因**：从对话发起的 Work 一律自动批准（`work_decided` 写死 `plan_approval: Auto`），人看不到任务列表，也就无法决定每个任务由哪个模型执行。人的诉求是「拆任务的模型写清每个 session 做什么，我来选每个任务用哪个模型」。

**改动**：

- `crates/orchestrator/src/work.rs`：`work_decided` 的 policy 改为 `PlanApproval::Required`；`land` 仍为 `Auto`，人在审批时可以改成「我审批」。
- `crates/orchestrator/src/brief.rs`：新增 `PLAN_WAITS`，在需要审批的 run 的 kickoff 里写明「先 `plan_submit` 写清每个任务，不要自己开工」。**只关闸门不够**——lead 的 guide 仍写着「能自己做就自己做」，它不交计划，人就没有可批的东西。

**代价**：小改动也要先过一张计划。要绕开就在计划审批里选「全托管」，或从 Home 发起。

**未改**：自动落地、任务并行度、预算默认值（仍为空，没有上限）。

### 7.1 实施记录

落点：`apps/gui/src/lib/projectView.ts`（项目成员、职责摘要、执行者与模板、独立会话、稳定排序）、`lib/todos.ts`（「需要你」的来源、去重、排序与跳转目标）、`workspace.ts` 的 `useProjectRuns`（项目内全部 run，不受侧栏 12 条上限限制）、`Sidebar.tsx` 与 `lib/sidebarTree.ts`、`views/Workspace.tsx` 与 `views/workspace.css`、`views/Session.tsx` 与 `ToolColumn.tsx` / `panes.ts`。回归测试在 `lib/*.test.ts`；mock 场景 `agent-workspace-sidebar` / `-overview` / `-edges` / `-narrow` 用 `apps/gui/scripts/screenshot.mjs` 查看。

已知缺口，留给后续：

- **run 审批项的等待时长只能近似。** 后端没有记录 run 进入 `awaiting_approval` 的时间，`updated_at` 又会被 `task_progress` 和策略编辑改动（用它排序会让顺序随流式活动跳动，违反 §4.1、§4.2），所以只能回落到 `created_at`。任务侧有 `Task.handoffs[].at` 可用，精度够。要修就得在协议里加一个进入状态的时间戳。
- **`Run.lead_note` 只记录「主导是副本」这个事实，不带模板 ID**，所以 run 的主导那一行只能展示 `lead_note` 文本，写不出「使用 X 的配置创建」。任务侧有 `worker_template` / `reviewer_template`，不受影响。
- **会话的「关联工作」只覆盖最近的 run 加本会话主导的全部 run**，很早的旧任务可能不在列表里：逐条拉全量 run 详情对每个会话、每次事件都太贵（§4.3 末）。
- **`views/Workspace.tsx` 与 `views/Session.tsx` 的新文案是中文字面量**，没有进 `lib/i18n.ts`；这是为了让三个界面改动并行而留的尾巴。
- mock 里没有 `cancelled` 的 run，结果页「已取消」分组只有计数 0 的样子可看。

现有落点包括 `apps/gui/src/Sidebar.tsx`、`lib/sidebarTree.ts`、`workspace.ts`、`activity` / `liveTurn`、`views/Run.tsx`、`views/Session.tsx` 和 `panes`。这些是接入位置，不预先承诺接口无需变化。

角色资格检查已在后端和界面候选列表中删除（§2.1）；剩下的 role 用法只是创建默认值，随 §6 迁移。

## 8. 验收场景

1. ~~Leo 的历史 role 为 planner，仍可被指定实现或评审，界面里也能选到 Leo~~（已实现，见 §2.1）；忙碌、跨工作区、来源本人等真实冲突仍明确报错。
2. 同一 Agent 在不同任务中承担不同职责；需要独立评审时不能通过改角色标签绕过约束。
3. 点击项目名称进入总览，点击箭头仅折叠，点击成员进入对应会话；三者互不混淆。
4. 流式输出和运行状态变化不导致成员位置跳动；226px 下名字、状态和摘要保持可辨认。
5. 两个待办来自同一 Agent 时都能找到；仅打开会话不清除待办；服务端确认处理后计数更新。
6. 项目折叠、搜索、归档来源和断线重连时，待办及工作记录不丢失；搜索退出恢复原折叠状态。
7. 新执行会话明确展示实际身份，不把它的消息与完成状态冒充原 Leo；归档后记录仍可访问。
8. 老 run 没有来源字段或尚未提交 plan 时，仍出现在项目总览；删除 run 不删父对话。
9. 自动审批策略下不凭空出现审批卡片；未读完成与真实待办分开处理。
10. 在浅色、深色、窄窗口、键盘操作和长中文标题场景下检查布局、焦点和可读性；切换会话不串计划或 diff。

实现时优先为分组、去重、状态和资格规则做有意义的回归测试；界面在 mock 场景下检查。

本轮实际核对情况：场景 2、3、5、7、8 在 mock 下看过（点侧栏里同一个 Agent 的第二条待办，进入会话后定位到的是第二张提问卡片、计数不变；计划页同时显示没提交 plan、没有来源记录和来源已归档的 run；`#c` 写「使用 Nova 的配置新建」而 `#a` 写「本人执行」；结果页把「完成 · 未落地」与「完成」分开）。场景 4 的 226px 可辨认性、场景 10 的浅色/深色/窄窗口/长中文标题看过截图；键盘焦点只做了代码审查，没有实测。场景 6 的断线重连、场景 9 的自动审批策略只有纯函数测试覆盖数据行为，没有实际跑过。
