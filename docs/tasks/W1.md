# W1 设计：轻量 Work，分工由主导按需提出

> 来源：2026-10-25 dogfood。在首页 Work 里发「你先熟悉一下项目」，run 立刻建好分支、拉起 Planner 和 worker；
> Planner 看完项目只回了一段概览，没有计划，run 就一直停在 `planning`，页面显示「正在拆解任务」。
> 先写设计，确认后再拆提交实现。

## 1. 问题

Chat / Work 这个切换本身对（对标 Codex 的「问」和「写代码」），问题在 Work 太重：

| 现象 | 原因 |
|---|---|
| 发一句话就要先填 9 个调度参数 | 首页 Work 表单把托管程度、默认 Worker、升级、Reviewer、并行数、三种上限都摆在前面，人还没说要做什么 |
| 「全托管」被记住，下次直接带上 | 托管程度存在 localStorage，上次的高风险选择悄悄延续 |
| 一选 Work 就是多 agent run | `create_run` 必然建 Planner 和 worker、进入 `planning`，期待 Planner 交计划；一句话能做完的改动也走这套 |
| 对话类请求卡在 `planning` | Planner 回复了人、没交计划，run 没有别的出口，只能取消 |
| Planner 在主仓库里干活 | Planner 的 `cwd` 是仓库根（`run.repo`），只有任务 worker 在 worktree 里；Planner 自己动手就直接改了人的工作目录 |
| run 页和 Planner 会话两张皮 | 对话在会话里，run 页只有状态，「发生了什么」要跳过去看 |
| 是否分工由人事先决定 | 违背「hub 是给模型用的」：要不要拆、拆几块，该由主导看过之后决定 |

## 2. 目标

- Chat 和 Work 都是**一句话起步**，切换是轻的，不先填参数。
- Work = 「去动手」：在独立分支和 worktree 里做，做完审查、落地；大多数改动一个主导自己做完。
- 分工是主导**按需提出**的升级：值得拆时交计划，人批准后才有任务和 worker。
- run 页就是这件事本身：主导的对话、改动、计划、任务、落地在一处。
- 托管程度和预算在**有计划时**选，默认最保守；选过的档位（含「全托管」）下次沿用。

## 3. 两种模式的区别

| | Chat | Work |
|---|---|---|
| 改动落在哪 | 直接在所选项目的工作目录（或无项目时 hub 给的目录） | run 分支的集成 worktree（`<home>/worktrees/<run>/integration`），人审查后落地 |
| 有没有 run | 没有；需要时主导提议转 Work（§6） | 有，从第一句话开始 |
| 能不能分工 | 可以招帮手（`agent_spawn` / `agent_send`），没有任务和落地 | 主导交计划后变多任务（§5） |
| 首页参数 | 项目、模型、推理强度 | 同左；高级参数收起（§7） |

Chat 并不是只读：它和今天一样能改文件，区别是 Work 的改动先在旁边做、看过再进主分支。这和 Codex 本地模式 / worktree 模式的分法一致。

## 4. Work 的生命周期

```
发起 ──▶ working ──▶（主导交计划）──▶ awaiting_approval ──▶ running ──▶ 收尾 / 落地 ──▶ completed
             │                                                  ▲
             └─────────────（主导自己做完，run_finish）──────────┘
```

### 4.1 发起

首页 Work 发送时：

1. `POST /v1/runs` 只需 `request`、`planner`（主导）以及可选的 `title`。`worker`、`escalate`、`reviewer`、`max_parallel` 改为可选，缺省在交计划时再定（§5.2）。
2. hub 照旧建 run 分支和集成 worktree，然后把**主导放进集成 worktree**：
   - 首页新建的主导：`create_run` 把它的 `cwd` 改成集成目录（它此时还没启动会话）。
   - 复用的已有 agent（从会话里转 Work、或首页挑了已有队友）：按模板克隆一个主导到集成目录，像任务 worker 从模板克隆一样，原 agent 不动。
   - 集成目录的环境照 DOGFOOD §1 带 `CARGO_TARGET_DIR=<集成目录>/target`。
3. 不启动 worker。首页仍按「自动」规则传一个 worker 模板（同一项目里按模型复用，例如 Sage），它只是模板：没有任务就不会有会话。API 不传 `worker` 时用主导自己作模板。
4. 无 git 的项目（`in_place`）：主导直接在项目目录里做，和今天一样只能一个任务一个任务来；首页在 Work 下提示「这个目录不是 git 仓库，改动直接落在原地」。

### 4.2 working：主导自己做

`RunStatus::Planning` 的含义从「等计划」放宽为「主导在做、还没有任务」。线上的值保持 `planning`，不做数据迁移；界面上的叫法改成「进行中」，副标题看主导实际状态：

| 主导状态 | run 页显示 |
|---|---|
| starting / running | `✻ Lyra 正在做 · 看它在做什么` |
| idle，最后一轮是回复 | `Lyra 回复了你 · 去回复`（已先修：`views/Run.tsx`） |
| error / stopped | `Lyra 停了：<原因> · 重新开始` |

主导在这个状态下可以：

- 读写集成 worktree，跑检查（`checks_run`、`workspace_run`），和普通会话一样跟人来回对话。
- 交计划（`plan_submit`），升级成多任务（§5）。
- 自己做完就 `run_finish`：今天要求「所有任务已合并」，改为**没有任务时**直接把 run 置为完成待落地，总结给人，落地卡片出现（§4.3）。
- 判断这件事其实不需要改代码（例如「熟悉一下项目」），就直接回复人，并在回复里说明可以 `run_finish`（没有改动的 run 完成后不出现落地卡片，分支和 worktree 直接清掉）。

主导须知（`brief::kickoff` 与 `protocol.rs` 的主导说明）改写为：

> 你在 run 的集成目录里，改动会先留在 run 分支上，人看过再落地。能自己做完就自己做，做完 `run_finish`；
> 改动大到值得几个人并行（互不依赖的几块、或要不同模型），再 `plan_submit` 交计划。只是回答问题或看项目时，
> 直接回复人。

### 4.3 收尾与落地

不变的部分：落地卡片、run 总 diff、`run_land`、托管策略里的 `land`。变化：

- 没有任务的 run 完成时，总 diff 就是集成 worktree 相对 base 的改动（含主导自己的提交）。主导没提交的改动，`run_finish` 时由 hub 提交一次（同 `task_complete` 的 `git add -A`），提交信息用主导给的 `message`，缺省用总结的第一行；人点「结束 run」时用 `crossagents: <标题>`。
- 派发任务、合并任务、落地之前，hub 都先把主导留在集成目录里的改动提交掉，任务才能从「主导做到哪」开始，合并也不会被未提交的改动挡住。
- 落地的条件从「至少合并了一个任务」放宽为「run 分支相对 base 有改动」（合并的任务或主导的提交）。
- 改动为空：run 直接 `completed`，结束通知写「没有改动」，落地会被拒绝。
- 主导住在集成目录里，run 结束后人还可能接着和它说话，所以集成 worktree 和分支不随结束清掉；清理在主导被归档或删除时做（§11）。落地卡片在没有改动时隐藏按钮，留给 W1-4。

## 5. 升级成多任务

### 5.1 交计划

`plan_submit` 的入口不变，变的是它在什么状态下能用：`planning`（working）时随时可交。今天它要求 run 在等计划，这一点不变；新增的是**会话里**的入口（§6）。

### 5.2 批准卡片里选托管和分工

计划交上来后，批准卡片（run 页和主导会话里各一张，同一个数据）显示：

- 任务列表（今天已有）。
- **托管程度**：我审批 / 半托管 / 全托管，默认「我审批」。选过的档位下次沿用，「全托管」也一样（后来改的：人要更托管）。
- **谁来做**：计划里每个任务可以已经指定队友或模型；没指定的用「自动」（按主导的登录挑同厂商便宜一档的模型，今天的 `workerModelFor`）。
- **上限**：预算、时间、token、并行数，收在「更多」里。

批准后才建 worker（克隆到各自 worktree），与今天 `approve_locked` 之后的流程一致。

托管策略已经是「我审批」以外的档位时（run 发起时就选了半托管 / 全托管，见 §7），`plan_approval=auto` 照旧自动批准，卡片只做展示。

实现（W1-2）：`POST /v1/runs/{id}/approve` 可带 `ApproveRunRequest`（`policy`、`max_parallel`、`assignees` 按任务 key 给 worker 或 `null`），都可省略，空 body 等于照计划批准。被选中的 worker 加入 run 的团队。卡片里「自动」是 run 的默认 worker（首页目前仍按 `workerModelFor` 建好传入）；选「新建」某个模型时，GUI 在批准前用主导的登录在仓库目录建一个 worker（已有同款就复用）。run 页的卡片和会话里的 PlanDock 共用 `usePlanApproval`。

### 5.3 运行中

不变：任务、依赖、审查、合并、`task_create` 追加任务、预算暂停、`human_ask`。

## 6. 会话里转 Work

会话（Chat）里的主导判断「这件事该在旁边分支上做」时：

- 新工具 `work_start { request, title? }`，只给会话组（`Group::Conversation`）。它不直接建 run，而是在会话里放一张卡片：「Lyra 想在独立分支上动手：<title> · 开始 / 不用」。
- 人点「开始」：hub 用这段 `request` 发起 Work（§4.1），主导是当前会话 agent 的克隆，落在集成目录。会话本身不变，卡片换成指向 run 的链接。
- `request` 由模型写，应包含会话里已经商定的内容：新会话在别的目录启动，接不上原会话的上下文。
- 人点「不用」：卡片收起，模型收到「人选择不开 Work」，可以在当前目录直接做或继续聊。

`plan_submit` 在会话里的拒绝信息改为指向 `work_start`，不再说「去首页发起 Work」。

实现（W1-5）：卡片是一条 `HumanItem`（`action: work`，`text` 是标题，新增的 `detail` 存 request），走现有的「问你」卡片和 `/v1/questions/{id}/answer`。「开始」先建 run（主导 = 会话 agent，默认 worker 也是它，托管「我审批」），成功后卡片才关，`run_id` 记在卡片上，GUI 跳到 run 页；建不成时卡片保持打开、报错给人。「不用」或关掉卡片都告诉模型人没开。会话不在 git 仓库里、或调用者本身是某个 run 的主导时，`work_start` 直接拒绝。会话指南（`protocol.rs` CONVERSATION）改为提示 `work_start`。

## 7. 首页

| 现在 | 改后 |
|---|---|
| Work 下展开 9 个字段 | 默认只有输入框、项目、模型、推理强度，和 Chat 一样 |
| 托管程度下拉框，记住上次的值 | 收进 ⚙「更多」。缺省「我审批」；记住上次选的档位，包括「全托管」 |
| 默认 Worker / 升级 / Reviewer / 并行数 | 不在首页。交计划时在批准卡片里定（§5.2）；在 ⚙ 里可预设，作为卡片的默认值 |
| 预算、时间、token 上限 | 收进 ⚙；选了「全托管」又没设任何上限时，在发送按钮旁提示「没有上限」 |

Work 的发送按钮旁写一行小字说明去向：「在新分支 crossagents/… 上做，看过再合并」。

实现（W1-3）：首页的 ⚙ 本来就收着这些字段，这一步改的是记忆规则（`crossagents.preset` 只存、只读「我审批」「半托管」）、输入框下方的去向说明（非「我审批」时带档位，点它打开 ⚙；全托管且无上限时标「没有上限」），以及 ⚙ 里「全托管（只这一次）」的写法。

## 8. run 页

- 顶部不变：标题、状态、主导、取消。
- 正文以主导的对话为主体：run 页直接嵌入主导会话的消息流（今天的会话视图组件），在它上面是请求和元信息，下面是输入框，人可以在 run 页里直接回复主导。
- 计划批准卡片、任务板、落地卡片插在对话流里出现的位置（按时间），任务板同时在右侧工具列可开。
- 侧栏里 run 下的主导一行仍然可点，进入同一个视图。

实现（W1-4）：`RunView` 直接用主导的 `SessionView`，传入 run 的顶栏（`header`）、元信息（`top`，请求不再单列，它就是对话的第一条）、收尾卡片 / 笔记 / 追溯（`bottom`）和任务板（`side`，窗口够宽时占右侧栏，否则接在对话后面）。计划批准用输入框上方的 PlanDock，run 页不再单放 PlanCard。落地卡片在 run 分支对 base 没有 diff 时写「没有改动，不用落地」并隐藏按钮。卡片按时间插进对话流没做，放在对话末尾。

## 9. 兼容

- 已有 run：数据不迁移。`planning` 状态的旧 run 显示为「进行中」，主导的 `cwd` 仍是仓库根，继续按旧方式工作；新规则只对新建的 run 生效。
- API：`CreateRunRequest` 的 `worker` 从必填改为可选（`ts(optional)`），旧客户端照常传。`RunConfig.worker` 改为 `Option<AgentId>`，读旧数据时为空即「交计划时定」。
- CLI：`crossagents run start` 的 `--worker` 变为可选。

## 10. 不做

- 不去掉 Chat / Work 切换，也不合并成一个模式。
- 不让会话里的主导直接建 run（不经人点「开始」）：开分支、开 worktree 是人看得见的动作，留一次确认。
- 不把原会话的历史搬进 run：不同目录的会话接不上，靠 `work_start` 的 `request` 交接。
- 不给「working」单独加 `RunStatus` 变体：保持 `planning` 线上值，避免改存储和事件。

## 11. 待定

- 主导自己做的改动要不要也走一次审查（reviewer）？倾向：托管策略里有 reviewer 时，`run_finish` 前由 reviewer 看一遍 run 总 diff；没有就跳过。
- 没有改动的 run 是否在侧栏保留：倾向保留到人归档，便于回看对话。
- `work_start` 卡片是否允许人改 `request` 再开始。
- ~~主导住着的集成 worktree 什么时候清~~ 已定：run 结束后主导被归档或删除时清掉（`lead_left`）。之后又改的先提交；分支在已落地或没有改动时一起删，否则留着等落地。归档的主导恢复时重新检出 run 分支，分支已删就从 base 新建（`lead_returned`）。

## 12. 实现拆分

| 步 | 内容 | 主要位置 |
|---|---|---|
| W1-1 | 主导进集成目录；`worker` 可选；无任务的 `run_finish` 与落地；主导须知改写 | `engine.rs`、`brief.rs`、`protocol.rs`、`landing.rs`、`api-types` |
| W1-2 | 批准卡片里选托管、谁来做、上限；批准后建 worker | `plan.rs`、`engine.rs`、`views/Run.tsx` |
| W1-3 | 首页收起参数、托管默认与记忆规则、去向说明 | `views/Home.tsx`、`lib/policy.ts` |
| W1-4 | run 页以主导对话为主体，卡片插进对话流 | `views/Run.tsx`、会话视图组件 |
| W1-5 | 会话里 `work_start` 与卡片 | `tools.rs`、`messaging.rs`、`human.rs`、会话视图 |

W1-1 是地基；W1-2、W1-3 依赖它；W1-4、W1-5 可以并行。每步一个提交，验收用真实 CodeBuddy / Codex 跑：

- 「熟悉一下项目」发在 Work 里：主导回复概览，不卡「拆解任务」，`run_finish` 后没有落地卡片、分支已清。
- 「给 README 加一节安装说明」：主导自己改、`run_finish`，落地卡片显示 diff，落地后 main 上有一次提交。
- 「把三个 crate 的错误类型统一」：主导交计划，批准卡片里选半托管，三个 worker 并行，全部合并后落地。
