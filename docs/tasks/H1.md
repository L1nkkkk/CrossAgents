# H1 任务书：托管式 hub 接口

> 依据：2026-10-22 讨论（hub 只转达、不替人说话；合并由 Planner 自己做；验收命令可选；不内置催促）· 状态：H1-1 至 H1-6 全部完成（各阶段的出入见 §9） · 2026-10-22

## 1. 目标

把一件事交给团队后，人只在两种时候出现：开始时说要什么，以及 agent 真的需要人拍板时。其余的拆活、招人、派活、检查、返工、合并、落地，全部由 agent 用 hub 的工具自己完成。

hub 的定位是本地协作底座，只负责六件事：会话、通讯、隔离、边界、状态、定时，外加全程记录。它不做决定，也不写提示文字：消息正文永远由某个 agent 或人写，hub 只附结构化字段（来源、任务、分支、diff 统计）。

## 2. 原则

| 原则 | 含义 |
|---|---|
| 转达，不代言 | hub 不再有 `prompts.rs` 那种模板消息。Worker 的总结原样转给发起人；派活的正文就是发起人写的任务描述 |
| 发起人负责 | 谁创建任务，谁就收到它的完成、提问、失败，也由谁来检查、合并或打回。发起人可以是 Planner，也可以是把子任务拆出去的 Worker |
| 能力而非流程 | hub 不再按固定流水线推进（验收 → 审查 → 合并）。它提供工具，顺序由 agent 决定 |
| 边界由 hub 守 | 隔离目录、角色权限、预算、托管策略、不碰人的工作区，这些由 hub 强制执行，不靠提示词约束 |
| 只呈现，不催促 | 「停了 · 未上报」只是一个状态。要提醒，由发起人自己设定时器，到点叫醒的是发起人 |
| 人的介入可配置 | 每处要人参与的地方（批准计划、落地、问人）都由托管策略决定。问人可以带超时和默认答案，避免整个 run 卡在人身上 |

## 3. 权限

工具按「权限组」开放，而不是只按三个固定角色。一个 agent 可以属于多个组。

| 组 | 谁 | 说明 |
|---|---|---|
| 所有人 | 每个由 hub 拉起或已登记的 agent | 身份、通讯、提醒、问人、笔记、查看状态 |
| 主管（lead） | Planner，以及策略允许的其他 agent | 招人、建任务、检查、合并、落地 |
| 经办人 | 某个任务当前的负责人 | 只能操作自己的任务：进度、完成、提问、失败 |
| 审查人 | 被请求审查某个任务的 agent | 只能对这个任务提交审查结论 |

经办人也可以把自己的任务拆成子任务交给别人，前提是策略允许 Worker 再派活。这时它就是这些子任务的发起人，可以对它们使用主管组里与任务相关的工具。

## 4. 托管策略（人设置一次）

托管程度的设置都在这里，挂在 run 上，也可以设为全局默认值。

| 设置 | 取值 | 缺省 |
|---|---|---|
| `plan_approval` | `required`：人批准后才开工；`auto`：直接开工 | `required` |
| `land` | `manual`：人来落地；`auto`：Planner 可直接合进 base 分支；`pr`：Planner 只能开 PR | `manual` |
| `human_ask` | `allow`：可以问人；`timeout:<时长>`：到点按默认答案继续；`deny`：不许问人，自己决定 | `allow` |
| `budget` | token、美元、时长的上限；到 80% 通知发起人，到 100% 暂停 run 并问人 | 不限 |
| `spawn` | 能否招人、最多多少个 agent、允许用哪些插件和模型 | 允许，上限 8 个，使用团队已有的插件 |
| `delegate` | Worker 能否再拆子任务派给别人 | 不允许 |
| `max_parallel` | 同时在跑的任务数 | 3 |

完全托管的设置是 `plan_approval=auto`、`land=auto`（或 `pr`）、`human_ask=timeout:30m`，再加一个预算上限。

## 5. 接口（MCP 工具）

工具名统一用 `名词_动词` 形式。任务可以用 `task` 参数指定，填 key（`#auth`）或 id 都行。所有返回都是结构化 JSON。

### 5.0 通用约定

| 约定 | 规则 |
|---|---|
| 幂等 | 模型会重试：超时、上下文压缩后重放、被打断后重做。每个写操作都按自己的业务键幂等，重复调用返回第一次的结果，并带 `repeated: true`：`task_create` 按任务 key；`agent_spawn` 按名字；`note_write` 按 key 覆盖；`task_accept` / `task_drop` / `task_cancel` 对已经处于目标状态的任务直接返回成功；`run_land` 对已经落地的 run 同理。唯一没有业务键的是 `agent_send`，它接受可选的 `idempotency_key`，另外 hub 会把短时间内发给同一收件人的相同正文合并为一条。不强制要求模型自己生成幂等键：上下文压缩后它会生成新的键，恰好防不住最该防的那类重试 |
| 线程 | 每条消息都有 `id`。`agent_send`、`task_answer`、`human_ask` 的回答都可以带 `reply_to`，hub 据此推出 `thread`（线程根）。GUI 用它分组、折叠，显示谁在回复谁 |
| 默认答案 | 凡是超时后按默认值执行的结果，都带 `defaulted: true`，事件流里记为 `human.defaulted`。`run_finish` 发给人的通知里，hub 会自己附上本 run 所有按默认值执行的决定，不依赖 agent 在总结里提到 |
| 通知合并 | hub 发给某个 agent 的通知（任务事件、`watch`、提醒触发、转达的完成报告）如果赶上它正在忙，会合并成一条待投递的「汇总」，同一任务的多条只保留最新状态。所以每个 agent 最多只有一条通知消息在排队，在它下一轮开始时送达。别的 agent 写给它的消息不合并，照常排队 |
| 配额 | 每个 agent 最多同时挂 20 个 `watch`、20 个 `remind_set`，超出时报错并列出现有的。`task_progress` 只更新卡片，不唤醒任何人 |

### 5.1 身份与团队（所有人）

| 接口 | 功能 |
|---|---|
| `whoami` | 我是谁：名字、角色、所属组、当前 run、正在负责和发起的任务、可用工具、预算余量 |
| `agent_list` | 所有队友：名字、头衔、专长（人设）、插件和模型、状态、当前任务、最近动作 |
| `agent_get` | 单个队友的详情，包括上下文占用和最近几轮的摘要 |

### 5.2 通讯（所有人）

| 接口 | 功能 |
|---|---|
| `agent_send` | 给一个或多个队友发消息（`to` 可以是名字、名字列表，或 `@team` 表示本 run 全体）。可关联任务；可带 `reply_to`；可加 `now` 插队并打断对方当前一轮；返回消息 id 和 thread。如果 `reply_to` 指向一个待回答的 `task_ask`，效果等同 `task_answer` |
| `message_withdraw` | 撤回一条对方还没开始处理的消息 |

### 5.3 提醒与关注（所有人）

| 接口 | 功能 |
|---|---|
| `remind_set` | 在多久之后（或某个时刻）叫醒我，附一句备注，可关联任务。可以设成「如果到那时任务还没完成才提醒」 |
| `remind_list` / `remind_cancel` | 查看或取消我设的提醒 |
| `watch` | 关注某个任务或队友，在指定变化（完成、失败、提问、停了未上报、空闲）发生时通知我。发起人默认会收到自己任务的这些事件，不用另外关注 |

### 5.4 找人（所有人，受 `human_ask` 策略约束）

| 接口 | 功能 |
|---|---|
| `human_ask` | 向人提问，可以带选项、默认答案和超时。只阻塞提问的这个 agent；问题出现在 GUI 的「需要你」里；回答作为一条 `reply_to` 指向这个问题的消息送回来。超时后按默认值执行时，回答会带 `defaulted: true`，人之后仍然可以在 GUI 里改答 |
| `human_notify` | 告诉人一件事，不需要回答，比如阶段汇报、完成报告、风险提示 |

### 5.5 共享笔记（所有人）

| 接口 | 功能 |
|---|---|
| `note_write` | 写一条笔记，按 key 覆盖。范围可以是本 run 或团队长期，用来记约定、决定、接口说明，供后来者读 |
| `note_read` / `note_list` | 读一条笔记，或按前缀列出笔记 |

### 5.6 招人（主管，受 `spawn` 策略约束）

| 接口 | 功能 |
|---|---|
| `agent_spawn` | 按需招一个队友：插件、模型、角色、人设，可以直接绑定任务。用于「这个任务用便宜模型」「来个安全审查」这类情况 |
| `agent_retire` | 让临时队友下线并移除，它的会话记录保留 |
| `agent_set_model` | 换某个队友的模型，从下一轮起生效（任务卡住时升级到强模型） |
| `agent_interrupt` | 打断某个队友当前的一轮 |

### 5.7 任务（主管建；发起人管）

| 接口 | 功能 |
|---|---|
| `plan_submit` | 一次提交整份计划，内容同 `task_create` 的批量形式。只在 `plan_approval=required` 时使用，提交后等人批准 |
| `task_create` | 建一个或一批任务：key、标题、要做什么、范围（允许和禁止改的文件）、依赖、负责人（或招人参数）、审查人、可选验收命令、可选提醒时间。负责人确定、依赖满足后，hub 自动建好 worktree 并把描述发给负责人 |
| `task_update` | 改任务的描述、范围或依赖。如果已经在做，把改动作为消息发给负责人 |
| `task_assign` | 换负责人。原负责人的 worktree 和分支交给新人继续用 |
| `task_cancel` | 取消任务。可选择保留或丢弃分支 |
| `task_list` | 本 run 的任务，可按状态、负责人、发起人筛选 |
| `task_answer` | 回答负责人用 `task_ask` 提的问题（`reply_to` 指向问题），任务从「等回答」回到运行中。这是关闭等待状态的明确入口 |
| `task_get` | 单个任务的完整情况：描述、状态、负责人、分支和 worktree 路径、Worker 总结、提问记录、检查结果、diff 统计、历史事件 |

### 5.8 检查（主管、审查人，以及发起人）

| 接口 | 功能 |
|---|---|
| `workspace_diff` | 任务分支相对集成分支的 diff，可以只看部分路径，也可以只要统计 |
| `workspace_read` | 读 worktree 里的文件（某个路径、某个范围） |
| `workspace_run` | 在任务的 worktree 里运行一条命令（测试、构建、运行脚本），返回退出码和输出，可设超时。由 hub 执行，所以检查方不需要自己有那个目录的沙箱权限 |
| `checks_run` | 运行任务上登记的验收命令，返回每条的结果。这是可选的便宜机械检查，不经过模型 |
| `review_request` | 请某个队友审查这个任务，hub 把 diff 和描述转给它 |

### 5.9 收尾（发起人；落地受 `land` 策略约束）

合并分两层，各自只有一个入口：

```
task 分支 ──task_accept──▶ run 分支（集成） ──run_land──▶ base 分支（如 master）
  每个任务一条              每个 run 一条                 你的分支
  发起人逐个任务调用         lead 在收尾时调用一次          受 land 策略约束
```

run 分支里只有被 `task_accept` 过的任务，所以 `run_land` 绕不过逐任务的认可。`run_land` 还要求所有任务都已结束（合并、放弃或取消），否则拒绝执行，并列出还没结束的任务。

| 接口 | 功能 |
|---|---|
| `task_accept` | 第一层：认可单个任务，把它的分支合进 run 分支。只有这个任务的发起人能调用。如果有冲突，返回冲突的文件和片段，不会自动失败；发起人可以自己解决，或打回给负责人 |
| `task_rework` | 打回：把修改意见作为消息发给负责人，任务回到运行中 |
| `task_drop` | 放弃这次结果，丢弃分支。任务关闭，或者重新排队换人做 |
| `branch_sync` | 把集成分支的最新内容合进某个任务的 worktree，让它基于已合并的依赖继续干活，返回有没有冲突 |
| `run_land` | 第二层：把 run 分支落地到 base 分支，方式可以是 merge、squash 或 PR。只有 lead 能调用，每个 run 一次。以下情况会拒绝执行：base 所在工作区有未提交改动；还有任务没结束；`land=manual` 时（这时改为在「需要你」里请人落地） |
| `run_finish` | 宣布 run 结束，附总结，同时通知人。hub 会在通知里附上本 run 所有按默认值执行的决定，以及花费。可以选择保留或清理还在跑的队友 |

### 5.10 经办（经办人）

| 接口 | 功能 |
|---|---|
| `task_progress` | 一句话进度（可带百分比），显示在任务卡片和侧栏上，不打扰发起人 |
| `task_ask` | 向发起人提问，返回问题 id。提问期间任务状态是「等回答」，直到发起人调用 `task_answer`，或发来一条 `reply_to` 指向这个问题的消息 |
| `task_complete` | 报告完成并附上自己写的总结。hub 提交改动，把总结连同 diff 统计转给发起人；登记了验收命令的话，顺便跑一遍并附上结果 |
| `task_fail` | 放弃并说明原因（做不到、描述有误、依赖缺失），转给发起人 |

### 5.11 审查（审查人）

| 接口 | 功能 |
|---|---|
| `review_submit` | 提交审查结论：通过或不通过，附意见（逐条要改的地方）。结论转给请求审查的人，由它决定是合并还是打回 |

### 5.12 用量（所有人）

| 接口 | 功能 |
|---|---|
| `usage_get` | 本 run、每个队友、每个账号的花费和额度窗口，以及离预算上限还差多少 |

## 6. 事件与状态

hub 只发事件、改状态，不说话。GUI 和 `watch` 都基于这些：

- 任务新增状态「停了 · 未上报」：负责人一轮结束了，却没有上报、提问或失败。
- 新事件：`human.asked` / `human.answered` / `human.defaulted`、`task.asked` / `task.answered`、`reminder.fired`、`note.written`、`agent.spawned` / `agent.retired`、`task.accepted` / `task.reworked` / `task.dropped`、`run.landed`。
- 每条转达的消息都带 `from`（谁写的）、关联的任务、`reply_to` 和 `thread`，GUI 据此显示任务卡片，并把同一线程的消息分组、折叠。

## 8. 已定（2026-10-22）

| 问题 | 决定 | 理由 |
|---|---|---|
| 固定流水线是否保留 | **不保留**。迁移期间（H1-1、H1-2）它照常工作，H1-3 换成工具后删除 `engine.rs` 里的 verify、merge、nudge、retry、escalate 和 `prompts.rs` | 两套路径意味着每个功能做两遍、测两遍。它能做的事，Planner 用工具都能做：自动检查用 `checks_run`，升级用 `agent_set_model` / `task_assign`。托管的目标也要求决定权在 agent 手里 |
| `workspace_run` 是否限制命令 | **不设允许清单**，但有硬边界：工作目录固定为该任务的 worktree；调用者必须是主管、审查人或发起人；超时缺省 5 分钟、最长 30 分钟；输出截断到 64 KB；每次调用记一条事件（命令、退出码、耗时） | Worker 本来就在 bypass 模式下能跑任意命令，主管的信任级别不低于 Worker。允许清单会挡住正常的检查（各种语言的测试和构建命令），换来的安全有限；真正的安全靠目录隔离和记录 |
| 笔记 | **两个范围**：`run`（随 run 结束只读归档，不再出现在 `note_list` 里）和 `team`（跨 run 长期保留）。人人可写，按 key 覆盖；`note_write` 传 `text: null` 表示删除，只有作者或主管能删；每次写入和删除都记事件，历史可查，不会真正丢失 | 团队约定（代码风格、目录结构、踩过的坑）跨 run 才有价值；限制删除权、保留历史，防止一个 agent 误删别人的结论 |

## 9. 分阶段实现

每个阶段单独可用、测试全过，并且合回 main 后不破坏已有功能。测试用 mock agent 的 `[call 工具 参数]` 指令编排各角色的动作；每个阶段完成时再用真实 Codex 走一遍（同 V4 §9）。

### H1-1 地基：消息、身份、通知

> 完成（2026-10-22）。与计划的出入：
> - 权限组暂时仍由角色推出：planner 对应主管，worker 对应经办人，reviewer 对应审查人。按任务关系计算放到 H1-3。
> - 「关注」增加了 `watch_list` / `watch_cancel`。
> - `message_withdraw` 只认最近一小时内由本人发出的消息，记录在内存里。
> - `agent_get` 暂不含最近几轮摘要。
>
> 测试见 `crates/mock-agent/tests/collab.rs`。

| 内容 | 说明 |
|---|---|
| 消息线程 | `MessageId` 对所有消息可见；`reply_to` / `thread` 写进 `agent.input` 事件和 `TranscriptTurn`；`agent_send` 支持 `reply_to`、`@team`、多收件人、可选 `idempotency_key`，以及短时间内相同正文去重 |
| 权限组 | `tools.rs` 从「按角色过滤」改成「按权限组过滤」。组由角色、run 策略和任务关系（经办人、发起人、审查人）共同算出，每次调用时重新检查 |
| 身份工具 | `whoami`、`agent_get`；扩充 `agent_list`（专长、当前任务、最近动作） |
| 通知汇总 | runtime 的 `Inbox` 加一个每 agent 一条的汇总槽位，可原地更新；hub 发给 agent 的通知都走它 |
| 提醒与关注 | `remind_set/list/cancel`、`watch`。存进 store（hub 重启后恢复），由 hub 里的一个定时任务触发；每个 agent 各 20 条上限；触发时进汇总槽位 |
| 事件 | `reminder.fired`、`watch.*` |
| GUI | 对话按 thread 分组、折叠，显示「回复 xx」 |
| 测试 | 线程字段往返；重复发送去重；汇总在忙时合并、空闲时立即送达；提醒到点触发、重启后仍在；超出上限报错 |

### H1-2 人：提问与托管策略

> 完成（2026-10-22）。实现要点：
> - `RunPolicy` 挂在 `RunConfig.policy` 上，旧数据按缺省值读入。`auto_approve` 仍然有效，等同于 `plan_approval=auto`。`ask_timeout_minutes` 可以是小数。
> - 问题和通知统一存为 `HumanItem`（迁移 0006），接口是 `GET /v1/questions`、`POST /v1/questions/{id}/answer`、`POST /v1/questions/{id}/dismiss`。
> - 新增 run 状态 `paused`。预算按事件流增量记账（`hub/src/budget.rs`），每 5 秒检查一次。用完时暂停 run，同时向人提一个带 `action: budget` 的问题：选「继续」，每个上限加 50% 并恢复运行；选「取消」，取消这个 run。
> - 「全局默认策略」还没做，目前每次建 run 时选择。
>
> 测试见 `crates/mock-agent/tests/human.rs`。

| 内容 | 说明 |
|---|---|
| 托管策略 | `RunPolicy`（§4 那张表）取代 `RunConfig.auto_approve` 等零散字段；有全局默认值，建 run 时可覆盖；旧数据迁移成等价策略 |
| 找人 | `human_ask`（选项、默认值、超时、`defaulted`）、`human_notify`；提问只阻塞提问者；超时由 H1-1 的定时任务驱动 |
| 预算 | 按 run 累计 token、美元、时长；到 80% 通知发起人，到 100% 暂停 run 并发起一个 `human_ask` |
| 事件 | `human.asked/answered/defaulted`、`budget.*` |
| GUI | 「需要你」里显示问题、选项、倒计时和默认值，可以直接回答；已按默认值执行的问题标出来并允许改答；新建 run 时可以选择托管程度（三档预设加自定义） |
| 测试 | 回答闭合等待；超时取默认值并带 `defaulted`；`deny` 策略下调用被拒；预算到 100% 时 run 暂停 |

### H1-3 任务改由 agent 驱动（核心，删掉固定流水线）

> 完成（2026-10-22）。实现要点：
> - `prompts.rs` 已删除。转达内容的排版放在 `brief.rs`：原文加上结构化事实（task_id、分支、改动统计、检查结果）。各角色的工作方式放在 `protocol.rs`，开会话时作为说明给一次，不在对话里重复。
> - 开场消息是人的需求原文，来源标为 `human`，后附团队名单；任务正文由发起人发出；完成报告、提问、审查结论都以写的人的身份转给发起人。
> - 任务状态新增 `stalled`；`passed` 的含义改为「已报告完成，等发起人检查」。旧数据里的 verifying / retrying / escalated 在 hub 重启时转成 stalled。
> - 验收命令改为可选：有就在 `task_complete` 时跑一遍，结果附在报告里。
> - `task_complete` 会立刻进入 `passed`，免得这一轮结束时被误判为停了；提交和检查在后台进行，完成后再转达。
> - 冲突：`task_accept` 返回 `merged: false` 和冲突片段，不改变任何东西。
> - 这一阶段 run 仍然在所有任务结束时自动结束；由 lead 收尾放到 H1-4。
> - 「停了 · 未上报」只通知发起人，不催 Worker。
>
> 测试在 `crates/mock-agent/tests/pipeline.rs`，共 12 个：接受、返工、停了、提问与回答、审查、冲突、运行中加任务等。

| 内容 | 说明 |
|---|---|
| 任务模型 | `Task` 增加 `issuer`；状态精简为 待开工 / 运行中 / 等回答 / 停了未上报 / 已完成待检查 / 审查中 / 已合并 / 已放弃 / 已取消；去掉 `attempts`、`escalated`、`nudges` |
| 任务工具 | `task_create`（批量、幂等）、`task_update`、`task_assign`、`task_cancel`、`task_list`、`task_get`、`task_answer`；`plan_submit` 改成「批量 `task_create` + 等批准」，验收命令可选 |
| 经办工具 | `task_progress`、`task_ask`（返回问题 id）、`task_complete`（提交改动，原文转达，登记了验收命令就顺便跑）、`task_fail` |
| 检查工具 | `workspace_diff`、`workspace_read`、`workspace_run`（§8 的边界）、`checks_run`、`review_request`、`review_submit` |
| 收尾工具 | `task_accept`（第一层合并，有冲突时返回冲突片段）、`task_rework`、`task_drop`、`branch_sync` |
| 删除 | `engine.rs` 的 verify、merge、nudge、retry、escalate；`prompts.rs`；`on_idle` 改为只把任务标成「停了 · 未上报」并通知发起人（走汇总） |
| 派活 | 依赖满足、有负责人时，hub 自动建 worktree，并把发起人写的任务正文原样发给负责人，附结构化字段 |
| GUI | 任务卡片换用新状态；「停了 · 未上报」进状态表；展开卡片可以看 diff 和检查记录；编排消息行改成「来自 Worker」的原文 |
| 测试 | 重写 `pipeline.rs`：Planner 建任务 → Worker 完成 → Planner 看 diff、跑命令 → 接受 / 打回 / 放弃；提问与回答；冲突时 `task_accept` 返回冲突；依赖任务在 `branch_sync` 后看得到前序改动；所有写操作重复调用都返回 `repeated` |

### H1-4 收尾与落地：第一次全托管

> 完成（2026-10-22）。实现要点：
> - 所有任务结束后，run 不再自动结束：hub 往 lead 的通知汇总里加一行事实，lead 调 `run_land`（policy 允许时）和 `run_finish`。人在 run 页上能看到「收尾中」，并有「合并进 main」「压缩合并」「结束 run」三个按钮（`POST /v1/runs/{key}/land`、`/finish`）。
> - 落地时，base 分支所在的 checkout 必须是干净的；base 没有被检出时，用临时 worktree 合并。PR 模式需要 `gh`。
> - `run_finish` 给人发一条通知：先是 lead 的总结，然后是合并和落地的情况，最后列出所有按默认值执行的决定。
>
> 验收（真实 Codex，codex-cli 0.163）：lead 用 gpt-6-luna，两个 worker 用 gpt-5.6-luna，「全托管 · 上限 45 分钟」，三个任务（实现、测试、文档），人没有任何操作。计划自动开工，lead 自己检查（checks_run、workspace_run）、接受了三个任务，并 `run_land` 到 main（e61ee58），然后写了总结。main 上 `python -m unittest` 5 项全部通过。
> 顺带发现：hub 启动的 shell 里，`python` 先命中 WindowsApps 的占位程序（退出码 9009），lead 自己改用了完整路径。这是本机 PATH 的问题，不归 hub 管。

| 内容 | 说明 |
|---|---|
| 落地 | `run_land`（merge / squash / PR，三种拒绝条件）、`run_finish`（hub 附上默认决定清单和花费）；`land=manual` 时在「需要你」里给人一个「落地」按钮 |
| 开工 | `plan_approval=auto` 时，`plan_submit` 直接开工 |
| 事件 | `run.landed`、`run.finished` |
| GUI | run 页显示落地状态、默认决定清单；「复制 git merge 命令」换成落地按钮 |
| 验收 | 用真实 Codex 跑一次全托管（`auto` / `auto` / 30 分钟默认答案）：给一个三任务的需求，人全程不操作，最后在 master 上看到结果和完整的决定记录 |

### H1-5 招人与升级

> 完成（2026-10-22）。实现要点：
> - 招来的队友在 `config.spawned_by_run` 里记下是哪个 run 招的，并加入该 run 的 team，所以可以按名字派活。`spawn` 和 `max_agents` 限制人数，按名字重复招人返回同一个。
> - 插件和模型缺省时，沿用 run 默认 worker 的插件和模型。
> - `agent_retire` 只能下线自己招来、且手上没有未结束任务的队友；会话记录保留。
> - `agent_set_model` / `agent_interrupt` 作用于本 run 的队友，包括任务上的 Worker 克隆。
> - 委派：任务新增 `parent`。子任务从父任务的分支开出，合回父任务的 worktree，由拆它的 Worker 作为发起人检查和接受。调度时父任务不阻塞子任务，也不占并行名额。
> - 还没做：run 不再强制要求预先指定 worker 模板（`CreateRunRequest.worker` 仍是必填）。等 GUI 支持「只选 lead」时再放开。
>

### H1-6 笔记、用量与外部 agent

> 完成（2026-10-22）。实现要点：
> - 笔记表在迁移 0007；每次写入和删除都发 `note.written` 事件，历史可查。`run` 笔记跟着所在的 run，run 结束后自然不再出现在列表里（一个 agent 只看得到自己当前 run 的笔记）。删除只能由作者或 lead 做。
> - `usage_get`：本 run 的花费（按 agent 报告的数据）、各 agent 的花费、各账号的额度窗口；在 run 里还附上预算上限和已用时间。
> - 外部 agent：插件名用 `external`。hub 从不启动它，发给它的消息先存在收件箱，它调 `inbox_read` 时取走，取走即视为读过。`POST /v1/agents/{key}/connect` 发放令牌，同时生成 mcpServers JSON 和 Codex config.toml 两种配置，以及该角色的工作说明。令牌只存在内存里，hub 重启后要重新生成。
> - GUI：团队页有「接入外部 agent」（登记、生成配置、一键复制）、外部队友卡片上的「连接配置」、团队笔记；run 页有这个 run 的笔记。
>

### 顺序与依赖

```
H1-1 地基 ──▶ H1-2 人 ──▶ H1-3 任务改由 agent 驱动 ──▶ H1-4 落地（第一次全托管）
                                                      ├──▶ H1-5 招人与升级
                                                      └──▶ H1-6 笔记、用量、外部 agent
```

H1-1 到 H1-4 是主线，做完就能全托管跑完一个 run；H1-5、H1-6 互不依赖，可以并行。
