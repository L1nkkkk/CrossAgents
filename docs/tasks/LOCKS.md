# LOCKS 任务书：本地资源锁与通用执行器

> 依据：2026-10-29 讨论（run 27bd5f0e 的 `run_finish` 检查撞上主导自己的另一轮 `cargo test`，Windows 链接器写不了正在运行的测试程序）及两轮评审 · 状态：已实现 L0–L3（L4 未做） · 2026-10-29

## 1. 目标与边界

同一台机器上，hub 的检查和 agent 的命令可能同时用同一份资源（构建目录、端口……），互相踩坏。现在只有规避，没有互斥（§2）。这一版要做到：

- **保证**：经过执行器（§4）的操作，在它声明的本地资源上严格互斥，按共享 / 独占区分；执行器正常结束时，等它起的整棵树清空才释放。执行器被强杀（崩溃、`taskkill /f`）时，锁**不保证**等到树结束：Windows 上实测锁在杀掉后 0.14–0.32 ms 内就释放，Job 里的进程还要 7–10 ms 才消失；这段时间里它们没有执行（100/100 次没有写资源），但这条顺序不是 Windows 的承诺，不当保证用。因此执行器拿到锁之后先查持有记录里的根进程（PID + 创建时间），还在就放锁继续等，这个检查补上了实测的窗口（§5）。不在 Job / 进程组里的进程（`CREATE_BREAKAWAY_FROM_JOB` 出去的、`setsid` 脱离的后代、绕过执行器起的）不在保证内；Unix 的弱保证见 §5：只有执行器自己起的、既没脱离进程组也没关掉继承 fd 的后代在保证内。
- **不保证**：不经过执行器的命令（人在终端里手敲、绝对路径调用 cargo、agent 没用 `exec` 的脚本）。这类冲突继续靠已有的手段：按 worktree 分开的构建目录、cargo 自己的锁、失败后由 `in_use_failure` 说明原因、按提示重试。
- **保留**：按 worktree 分开的构建目录（TOOLCHAIN §3）、落地前比对 HEAD 的乐观并发（`landing.rs` `LAND_ATTEMPTS`）。资源锁防止执行时互相干扰，HEAD 比对保证落地的就是检查过的版本，两件事互不替代。
- **不做**：跨节点共享的资源（多台机器共用的数据库、部署环境）。这类资源要由 hub 或资源自身协调，等多节点（TODO §八 B1）有了 hub↔node 通道再设计。v1 在资源声明里留 `scope`，写了 `shared` 就明确报错，不悄悄当作本地资源处理。
- **不承诺** FIFO：内核文件锁不排队，等待方式是带超时的轮询。

核心思路：**锁放在资源所在的机器上，用操作系统的文件锁实现，不起常驻服务；执行器只负责通用执行；hub 负责调度和展示。** 登记的是 `build` 指哪一份资源，不登记允许执行哪些命令，agent 可以用任何工具和自己写的脚本。

## 2. 现状（已核对代码）

| 位置 | 现在做什么 | 问题 |

## 3. 资源声明

```toml
[resources]
# 名字 → 实际路径（可用 {build}、{checkout}）+ 默认访问方式
build = { path = "{build}/cargo", access = "exclusive" }
# scope 默认 "local"；写 "shared" 在 v1 直接报错
```

- Rust 预设自带 `build`，和它注入的 `CARGO_TARGET_DIR` 指向同一个目录。项目里写了同名资源就覆盖预设的。
- **资源身份 = 规范化后的实际路径**（绝对路径、解析符号链接、Windows 上统一大小写和分隔符）。两个 worktree 的构建目录不同，资源就不同，互不阻塞；如果配置成共用同一个目录，会自动变成互斥，不用另外维护一套资源名字。
- 访问方式只有 `shared` 和 `exclusive`。`exec` 可以用 `--resource build:shared` 改写这一次的访问方式。

## 4. 执行器

一套库，两个入口：

```text
crossagents exec --resource build -- <任意命令>   ← agent / 人 / shim
hub 的检查（require_run_checks、任务验收、workspace_run）   ← 进程内直接调用同一个库
        ↓
解析资源 → 一次拿全所有锁 → 写持有记录 → 起进程树 → 等整棵树结束 → 删记录 → 放锁
```

### 4.1 锁文件放在固定目录

```text
<home>/locks/<规范化路径的 sha256 前 32 位>.lock
<home>/locks/<同上>.holders/<exec-id>.json
```

- 锁文件**不放在构建目录里**：`cargo clean` 或脚本会删掉构建目录，在允许删除已打开文件的平台上（Unix，以及 Rust 在 Windows 上用 POSIX 语义删除时），旧进程锁着旧文件，新进程会建一个同名的新文件、拿到另一把锁，互斥就失效了。
- `locks/` 下的锁文件运行期间不删除、不替换。清理只删一段时间没人碰、而且当前拿得到独占锁的锁文件。
- Windows 用 `LockFileEx`，Unix 用 `flock`，都分共享和独占。

### 4.2 拿锁：一次拿全，拿不全就全放

- 一次 `exec` 要的所有资源按锁文件名排序，依次**尝试**加锁（不阻塞）。有一个拿不到，就把已拿到的全部放掉，退避一段时间再从头来。任何时候都不会持有一部分资源去等另一部分，所以不会死锁。
- 等待期间每隔一段时间往 stderr 打一行：`waiting for build (C:\…\cargo): held by Kai · cargo test --workspace · since 02:43`，信息来自持有记录（§4.4）。
- 超时（`--timeout`，agent 默认 10 分钟；hub 检查用检查自己的时限）后以退出码 `75` 结束（取 BSD `EX_TEMPFAIL` 的含义，与命令自身的失败区分开），说明谁占着、占了多久。
- **hub 没启动时照样能用**：锁是本机文件锁，不依赖 hub。

### 4.3 进程树

- 用 `core::process::spawn_tree` 起命令，但**放不进 Job（或进程组）时不运行**，报错退出：没有进程树就无从保证“树结束后才放锁”。
- 正常路径：等根进程退出后，再等整棵树清空（Windows 查 Job 的活动进程数，Unix 查进程组）才放锁。常驻进程（开发服务器）在 `exec` 下跑多久就占多久资源，这是有意的：占着端口的服务就该占着锁。
- 执行器被强杀时，锁和进程树谁先没：见 §5，不预设结论。

### 4.4 持有记录与锁分开

- 锁文件只管互斥，不写内容。
- 每次 `exec` 单独写一份 `holders/<exec-id>.json`：exec-id、资源、访问方式、命令、agent / run（从环境变量读，可以没有）、根进程 PID 和创建时间、Job 名或进程组号、开始时间。多个共享持有者各写各的，不会互相覆盖。
- 记录**只能让 hub 多等，不能放行**：hub 展示用它；§5 的“前任进程树还活着就继续等”也只会让获取更保守。记录对应的进程已经不在了（PID + 创建时间对不上），展示时忽略，清理时删掉。

### 4.5 嵌套与重入

`exec` 把持有的锁通过环境变量传给子进程：`CROSSAGENTS_HELD=<exec-id>;<锁文件名>:<访问方式>:<句柄或 fd 号>,…`，句柄 / fd 设为可继承。内层 `exec`（包括 shim）收到请求时：

| 内层要的 | 外层持有 | 处理 |
|---|---|---|
| 同一资源，访问方式不高于外层（共享→共享、独占→共享、独占→独占） | 是 | 不再加锁，直接运行 |
| 同一资源，共享 → 独占（锁升级） | 是 | **立即报错**：升级要在外层声明 |
| 外层没持有的资源 | 否 | **立即报错**：在外层 `exec` 里一起声明 |

只凭继承来的名字不能断定锁还在。放行前要核验：环境变量里的句柄 / fd 有效，指向的确实是那个锁文件（比较文件 ID / inode），持有记录对应的外层 `exec` 进程还活着。核验不过就当作没有持有，按普通请求处理。

### 4.6 shim

- Rust 预设默认开启 `cargo` 的 shim：run worktree 的 `PATH` 最前面加 `<home>/shims/<版本>/`，里面的 `cargo.exe` 是 `crossagents.exe` 的硬链接（拿不到硬链接就复制），按 `argv[0]` 认出自己是 shim。不用 `.cmd`，避免 Windows 上参数转义和退出码出问题。
- shim 在 `PATH` 里跳过自己所在的目录，找到真正的 cargo，再按 `exec --resource build -- <真 cargo> <参数>` 执行。外层已经持有 `build` 时直接运行（§4.5）。
- 项目可以关掉：`[run] shims = []`。

## 5. L0：先验证平台行为，再写保证

“锁释放时进程树已经不在了”不能直接推出来：

- **Windows**：`KILL_ON_JOB_CLOSE` 是在 Job 的最后一个句柄关闭时终止 Job 里的进程。执行器被强杀时，内核关闭它的句柄，但锁的释放和 Job 里进程的终止谁先谁后，文档没有保证。竞争者可能在旧进程还在写构建目录时拿到锁。
- **Unix**：把 `flock` 的 fd 继承给子进程，可以让锁活得更久。但子进程可以关掉这个 fd，别的程序起后代时也未必保留它；任何共享这把锁的 fd 显式解锁，锁都会放掉。它保证的是“还有人持有锁 fd”，不是“所有后代都还被跟踪着”。

所以第一步是一个独立的小实验（`crates/core/tests/` 下，Windows 和 Linux 各跑），只回答一个问题：**执行器被强制终止时，竞争者有没有可能在旧任务还在访问资源时拿到锁。** 只验证“子进程最后被杀掉了”不算数。实验要覆盖：

1. 执行器在子进程持续写文件时被 `TerminateProcess` / `SIGKILL`，竞争者在拿到锁的那一刻检查旧子进程是否还活着、文件是否还在被写。重复足够多次，看有没有窗口。
2. Windows：锁句柄设为可继承、让子进程继承，看锁是否要等所有继承者都退出才释放。
3. Unix：子进程关闭继承来的 fd、或用 `setsid` 脱离进程组后继续写。
4. 命名 Job / 进程组号做“前任检查”：竞争者拿到锁后，按前任的持有记录打开它的 Job（`OpenJobObject` + 活动进程数）或探测进程组（`kill(-pgid, 0)`），还有活着的就放锁继续等。确认这个检查能不能补上 1 里的窗口。

根据结果在本节补上结论，写清楚哪个平台保证到什么程度。验证没过的平台，保证就写弱一些（例如 Unix 上“用 `setsid` 脱离的后代不在保证内”），不在提示词里说过头的话。

### 结论

实验在 `crates/core/tests/lock_kill_race.rs`，辅助进程是 `tests/support/lock_kill_helper.rs`（`[[bin]]`，测试用 `CARGO_BIN_EXE_*` 找到它）。做法是：执行器进程用 `LockFileEx` 独占锁、建一个命名 Job（`KILL_ON_JOB_CLOSE`）、把“每轮紧循环往文件里追加一行”的子进程放进 Job；测试用 `TerminateProcess` 杀掉执行器，随即空转抢锁；拿到锁的那一刻记三件事——旧子进程是否还活着（`OpenProcess` + `WaitForSingleObject(…, 0)`）、锁易手之后它又写了多少字节、前任的 Job 还在不在。“窗口”指拿到锁时旧子进程还活着或还在写。子进程的写循环没有 `sleep`（Windows 上 `Sleep(1)` 实际等 ~15.6 ms，太粗，分不出“在跑”和“被冻住”），只要还在执行就会一行接一行地写，所以“锁易手后的那几毫秒里写了 0 字节”是强证据，不是运气。反过来，同一个探针在子进程确实还在跑的那组（可继承句柄）50/50 次都测到了增长，说明它不会把“在写”误判成“没写”。

本机 Windows 11 Pro / rustc 1.99.1，2026-10-29 跑了两轮，每轮 100 次（继承句柄那组 50 次），两轮结论一致：

```text
cargo test -p crossagents-core --test lock_kill_race                      # 每项 5 次，只跑通并打数
cargo test -p crossagents-core --test lock_kill_race -- --ignored --nocapture
CROSSAGENTS_L0_ROUNDS=200 cargo test -p crossagents-core --test lock_kill_race -- --ignored --nocapture
```

| 场景 | 次数 | 窗口 | 实测细节 |
|---|---|---|---|
| 直接杀（Job 里，锁句柄不可继承） | 100 + 100 | 100 / 100 | 从杀到拿到锁 0.14–0.32 ms；旧子进程在锁易手后还“活着”6.6–9.9 ms 才退出；这段时间它写了 **0** 字节 |
| 加第 4 条的 Job 前任检查 | 100 + 100 | 100 / 100 | 每次 `OpenJobObjectW` 都失败——Job 随最后一个句柄一起没了，检查一次也没拦住（`held back` = 0） |
| 改成查根进程 PID + 创建时间 | 100 + 100 | **0** / 100 | 每次都是放锁重试（两轮累计约 15–16 万次空转），锁改成在前任根进程退出之后才拿到，代价是多等 7–9.5 ms |
| 锁句柄可继承、子进程继承（无 Job） | 50 + 50 | 50 / 50 | 50/50 次子进程确实拿到了同一个文件对象的句柄（卷序列号 + 文件索引核对过）；执行器一死锁立刻可用，子进程仍在写（50/50 次窗口内继续增长） |

三条结论：

1. **锁先没，进程树后没。** 执行器被强杀时 `LockFileEx` 的锁在 0.14–0.32 ms 内就没了，Job 里的进程还要 7–10 ms 才消失，“锁释放时进程树已经不在了”**不成立**。但这 7–10 ms 里旧任务没有执行：观察到的顺序是 Job 先把里面的进程停住、锁才易手（100/100 次 0 字节）。这个顺序 Windows 没有承诺，只是实测如此，**不能写进保证**，只能拿来解释“为什么现实中很少撞上”。结论是不让锁单独承担“旧任务已经停手”的证明。
2. **可继承的锁句柄不延长锁。** `LockFileEx` 的字节范围锁属于加锁的那个进程，不属于文件对象；把锁句柄设成可继承、子进程确实继承了，执行器一死锁照样立刻可用（50/50）。所以 §4.5 里的“句柄 / fd 设为可继承”只是给内层 `exec` 核验复用，**不能指望它兜住进程树**。顺带说明 §5 开头对 Unix 的猜测在 Windows 上没有对应效果。
3. **命名 Job 当不了前任检查，根进程 PID + 创建时间可以。** 最后一个 Job 句柄关闭时 Job 和里面的进程一起销毁，`OpenJobObjectW` 正好在最需要它的时刻失败（100/100）。改用 §4.4 记录里的根进程（PID + 创建时间）：拿到锁后先看它是否还是那个进程、是否还活着，是就放锁重试——“有就多等”的方向，100/100 次窗口消失（上表第三行）。它只覆盖记录里的那一个进程；根进程早于后代退出时看不到后代，这一点和 §4.3 的前提一样，靠 Job 兜。

Windows 建议的保证措辞（写进文档和提示词用）：

> 执行器正常结束时，等它起的整棵树清空才放锁。执行器被强杀（崩溃、`taskkill /f`）时，锁**不保证**等到树结束：实测锁在杀掉后 0.14–0.32 ms 内释放，Job 里的进程还要 7–10 ms 才消失；这段时间里它们没有执行（100/100 次没有写资源），但这条顺序不是 Windows 的承诺，不当保证用。因此执行器拿到锁之后先查持有记录里的根进程（PID + 创建时间），还在就放锁继续等；这个检查补上了实测的窗口。不在 Job 里的进程（`CREATE_BREAKAWAY_FROM_JOB` 出去的、或绕过执行器起的）不在保证内。

**Unix：未验证。** 本机是 Windows，`#[cfg(unix)]` 的对应实验写在同一文件里（`sigkill_releases_the_flock`、`inherited_fd_keeps_the_flock`、`child_closing_the_inherited_fd_drops_the_lock`、`setsid_writer_outlives_the_group`、`predecessor_group_check_closes_the_window`），**一次都没跑过**，结论待有人在 Linux 上跑完再补。在那之前按弱保证措辞：

- `SIGKILL` 执行器时 `flock` 随执行器进程消失立即释放，进程组里的子进程不会被内核带走（Unix 没有 Job），**只有执行器先杀组再退出才有“树结束才放锁”**。
- 把 `flock` 的 fd 继承给子进程，锁能活到最后一个持有该 fd 的进程退出；但子进程可以关掉它，`setsid` 脱离的后代也与这个 fd 无关，所以它保证的是“还有人拿着 fd”，不是“所有后代都被跟踪”。
- 前任检查用记录里的进程组号 `kill(-pgid, 0)`：`setsid` 之后的后代换了自己的组，检查看不到它。
- 因此 Unix 上只能这么写：“只有执行器自己起的、既没脱离进程组也没关掉继承 fd 的后代在保证内；`setsid` 脱离的后代、以及没经过执行器的进程，和手敲的命令一样不在保证内。”

## 6. hub 侧的改动

- `require_run_checks`、任务验收的检查、`workspace_run` 都改走执行器：先拿 `build`（以及检查声明的其他资源），拿到之后再跑。hub 自己的两次检查从此在同一个 checkout 上严格串行。
- **删掉 `refuse_while_running` 的拒绝**。经过执行器的操作就等锁；`running.rs` 的记录只用来展示活动、提示“可能有绕过执行器的命令在跑”，不再构成第二套互斥规则。事件记录不能可靠证明某个命令绕过了执行器，所以不拿它来做判断。
- `in_use_failure` 不变：检查失败、输出里有“文件被占用”时，仍然说明原因、提示重试。
- `protocol.rs`：加一句，在 checkout 里构建或测试的命令用 `crossagents exec --resource build -- …`（cargo 已有 shim，会自动进入执行器）；看到 `waiting for …` 是在排队，不要另起一轮同样的命令；退出码 75 是等锁超时，可以重试。
- run 页：显示每个资源当前的持有者（来自持有记录）和正在等的 hub 检查，不提供强制释放（强制释放要先杀掉对方的进程树，留到 L4 再说）。

## 7. 分阶段与验收

| 阶段 | 内容 | 验收 |
|---|---|---|
| L0 | §5 的平台实验 | 两个平台的结论写进 §5；保证的措辞按结论定 |
| L1 | 执行器库（锁目录、一次拿全、持有记录、嵌套核验、进程树）+ `crossagents exec` 子命令 + `[resources]` 解析 | 见下面的测试表 |
| L2 | hub 检查、任务验收、`workspace_run` 改走执行器；删掉 `refuse_while_running` 的拒绝；`protocol.rs` 加一句 | 同一 checkout 上，后台 `cargo test` 在跑时调 `run_finish`：检查等到它结束再跑，不报 LNK1104；并行调 `run_finish` 和 `run_land`，两次检查不重叠 |
| L3 | cargo shim | run worktree 里直接敲 `cargo test` 也进执行器；shim 不会嵌套加锁；`shims = []` 能关掉 |
| L4 | run 页显示持有者；GUI / CLI 里的强制释放（先杀树再放锁） | — |

L1 的测试，前四条是这一版能不能兑现保证的关键，必须有：

1. **执行器被强杀后的竞争**：同 §5 第 1 条，作为回归测试保留，按 L0 结论断言。
2. **构建目录被清掉**：持有 `build` 期间 `cargo clean` / 删掉整个构建目录，另一个 `exec` 仍然拿不到锁。
3. **共享锁重入请求独占**：外层 `build:shared`，内层要 `build`（独占）时立即报错，不等待、不死锁。
4. **子进程关掉继承来的句柄 / fd**：之后锁仍由执行器持有，直到整棵树结束；按 L0 结论断言后代脱离时的行为。
5. 两个 `exec` 抢同一个资源：后一个等待、打出持有者、前一个结束后再跑；超时退出码是 75。
6. 两个 worktree 各自的构建目录：两个 `exec` 同时跑，互不阻塞。
7. 多资源：A 拿 x 等 y、B 拿 y 等 x 的局面不会出现（一次拿全，拿不全就全放）。
8. 嵌套核验：伪造 `CROSSAGENTS_HELD`（句柄无效、指向别的文件、外层进程已退出）时，不能借此跳过加锁。
9. hub 没启动时 `exec` 照样互斥。
10. 声明 `scope = "shared"` 时报错。
