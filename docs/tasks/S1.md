# S1：会话属于工作区，run 只记录谁参与过

状态：已完成（2026-10-27，fbf76ce、66f66f6、77b603a 及其后的执行记录与 GUI 提交）。设计决定见 [DESIGN.md](../DESIGN.md) §4.7；实现和方案不一致处见 §7。

## 1. 起因

2026-10-27 讨论 run 的承接：run B 接着 run A 做，人选 run A 的 planner 当主导，希望由它决定是用新会话，还是用 run A 里用过的会话继续干活。run A、run B 在同一个工作区里，会话本应属于工作区。

现在的实现做不到，因为会话被 run 拥有：

| 环节 | 现在 | 位置 |
|---|---|---|
| 主导 | 用过的会话被**复制**一份放进 run 的集成工作区，从没开过会话的才挪本人进去 | `engine.rs::lead_in` |
| 派活 | 每个任务从队友**克隆**一个新会话，放进任务的 worktree | `engine.rs::fresh_agent`、`quota.rs::routed_worker` |
| 任务结束 | 克隆出来的会话被**删除**，对话一起没了 | `engine.rs::release_agents`、`tasks.rs::task_assign`、`review.rs` |
| run 招募 | 带 `spawned_by_run`，在数据上是 run 的附属 | `team.rs` |
| 删除 run | 主导副本和招募来的会话**一起删** | `delete.rs::owned_agents`（R1-B） |
| 送回原处 | 只为「被挪进去的主导」补了 `lead_home` | `delete.rs::send_home`（a567158） |

这些都基于一个错误前提，`lead_in` 的注释里写着："a vendor session cannot move"。实测并非如此：Claude Code 在别的目录 `--resume` 仍记得对话，Codex 的 `thread/resume`、`turn/start` 都能换 cwd（[claude-stream-json](../research/claude-stream-json.md) 第 42 行，[codex-app-server](../research/codex-app-server.md) 第 28 行）。

## 2. 目标

- 会话属于工作区。run 和任务通过执行记录（交接卡）关联会话，不拥有会话。
- run B 选 Pia 当主导，就是 Pia 本人，带着 run A 的上下文。
- planner 派活时默认新开一个**执行会话**；要接着用某个已有会话时，显式指定用本人。
- 任务结束、run 结束、删除 run，都不删会话：本人回到工作区，执行会话归档。归档的会话可以恢复，恢复后能再被指定用本人。

不做：跨工作区复用会话；同一个会话同时在两处干活；换账号时保留会话（会话存在账号目录里，换账号只能新开，靠交接卡延续）。

## 3. 改法

### 3.1 会话的家、执行位置与占用（core、store、hub）

- `Agent` 加 `home: PathBuf`，即它所属的工作区。`cwd` 保留，表示当前在哪干活，平时等于 `home`。
  - 迁移：`cwd` 在 `<worktrees>/` 下的会话，按所在 run 取 `run.repo`；其余取 `cwd`。有 `lead_home` 的取它，然后删掉这个键。
  - GUI 侧栏按 `home` 分组（现在按 `cwd`）。
- **占用**：一个会话同一时间最多被一个执行占着，主导、worker、reviewer 都算。存储层新增占用记录 `agent_claims(agent_id 主键, run_id, task_id 可空, role, since)`。
  - `Store::claim_agent(agent, run, task, role)` 用一条 `INSERT`：主键冲突就失败，返回当前占用者。`Store::release_agent(agent, run)` 只删除 `run_id` 相符的那一行。
  - 这是跨 run 的互斥。run 锁只管一个 run 内部，两个 run 各拿自己的锁，仍会同时通过「它空不空」的检查，所以占用必须落在数据库的原子操作上。
  - hub 启动时按未结束的 run 和任务核对占用表，删掉已结束的残留。
- 驱动能力加 `move_cwd: bool`：会话能在另一个 cwd 恢复。`claude-native`、`codebuddy-native`、`codex-native` 为 true，ACP 默认 false。
- `AgentHost::place(agent, dir)`：停掉空闲会话的进程、改 `cwd`，下一轮在新目录恢复。
  - 会话正在跑一轮，或有人发来的消息在排队时，返回 Busy（见 §3.3）。
  - **在新目录恢复失败时不静默新开**。runtime 现在「恢复失败就开新会话」的退路，对用本人的执行要关掉：这一轮报错，执行标为失败并写明「上下文没能延续」，占用释放，由 planner 决定改用新开的执行会话。普通聊天保持现在的退路。
  - `AgentHost::send_home(agent)` 就是 `place(agent, home)`，只在会话空闲时做；忙的时候记一个待办，这一轮结束后再送回。

### 3.2 主导（orchestrator）

- `lead_in`：选中的会话 `move_cwd` 为 true，且 `claim_agent(role = lead)` 成功，就 `place` 本人进集成工作区。
  - 占用失败（它在主导另一个未结束的 run，或正在执行任务）：建 run 时返回原因，由人改选或先结束那边。
  - `move_cwd` 为 false：才复制（保持现状作为退路），并在 run 上记一句「主导是复制出来的，没带上原会话的上下文」。
- run 结束（finish、land 之后、cancel）以及删除时，按 §3.4 释放占用。
- R1-A 的 `home_of` / `run_lived_in` 改成直接读 `agent.home`。`lead_home` 及 `delete.rs::send_home` 删掉，由 §3.1 取代。

### 3.3 派活（orchestrator、协作工具）

- 规格里的 `assignee`（`plan_submit`、`task_create`）、`task_assign` 的 `to`、reviewer 指派都加 `fresh: bool`，**默认 true**：
  - `fresh: true`（默认）：按这个队友的配置新开一个执行会话，也就是现在的行为。界面上叫「执行会话」，用完归档，不删。
  - `fresh: false`：用这个会话本人，带着它的上下文。
- `fresh: false` 时 hub 依次检查，不满足就让工具返回原因、任务不派出，由 planner 改选、改用新开或稍后再试：
  1. 同一工作区（`home` 相同）；
  2. 驱动 `move_cwd`；
  3. 没归档。已归档的返回「先恢复」；人可以在 GUI 恢复，planner 也可以在 `fresh: false` 时带 `restore: true` 明确要求恢复；
  4. **人的请求优先**：它正在回人的消息，或有人发来的消息在排队，就返回 Busy。不允许后到的派活插到人已经发出的请求前面；
  5. `claim_agent` 成功（跨 run 原子占用）；
  6. 没在额度上被改派（换账号只能新开）。

  通过后 `place` 进任务的 worktree。
- 会话接了任务之后，人再发来的消息照常排队。会话页顶部显示「正在执行 run B · 任务 c」，并给出「中断」按钮：中断这一轮、执行标为被人打断、占用释放、会话回到工作区，由 planner 收到通知后改派。
- 额度改派（`routed_worker`）换账号时仍新开执行会话，交接卡照旧。

### 3.4 收尾不删会话，只释放这次的占用

- **只动属于被关闭 run 的占用**。收尾时按 `agent_claims` 里 `run_id` 等于这个 run 的行逐个处理，不按「谁参与过这个 run」去遍历：
  - 本人：`release_agent(agent, run)`，然后 `send_home`；
  - 执行会话：`release_agent` 后 `archive_agent`（停进程、移出列表、保留对话），不再 `remove_agent`。这一条吸收 [SELF](SELF.md) 的 A3。
- 参与过 run A、此刻被 run B 占着的会话，run A 收尾或被删除时不碰：它的占用行属于 run B，`release_agent(agent, run A)` 删不到它，也不会被送回家。
- 适用于：`release_agents`（任务结束）、`task_assign` 改派前的旧执行、reviewer 用完、`review.rs` 返工换人、run 结束、`delete_run`。
- `delete_run` 不再删任何会话。清单里 `agents` 改为两类：「回到工作区」和「已归档」，参与过但占用已不在本 run 的不列。`DeleteRunResponse` 相应调整，bindings 重新生成。
- `spawned_by_run` 保留，只作为来源记录（谁招来的），不再决定生死。

### 3.5 执行记录

- `Handoff` 加 `fresh: bool`（新开的执行会话，还是本人）和 `outcome: Option<HandoffOutcome>`。`outcome` 取值：delivered（交付）、reworked（被打回）、reassigned（被改派）、interrupted（被人打断）、failed（含「上下文没能延续」）、cancelled。这次执行结束时回填到这张卡上。
- run 页「参与者」：按任务列出执行，每条链接到会话。已归档的执行会话也能点开，并可以恢复。

### 3.6 planner 怎么知道有哪些会话可用

- 开场说明（`brief::kickoff`）的团队名单之外，加一段「工作区里的会话」：名字、模型、状态（空闲 / 忙于哪个 run 的哪个任务 / 已归档）、最近一次执行（哪个 run、哪个任务、结果），取自交接卡，最多列 12 个，按最近使用排序。说明里写明默认 `fresh: true`，要接着用某个会话写 `fresh: false`。
- `agent_list` 返回同样的字段。

## 4. 测试

- store：`claim_agent` 主键冲突时失败并返回占用者；`release_agent` 只删 `run_id` 相符的行；`home` 迁移（`<worktrees>/` 下的会话归到 run 的仓库；`lead_home` 被吸收）。
- hub：`place` 对空闲会话生效，下一轮的 cwd 是新目录、session id 不变（mock 驱动断言收到的 resume 参数）；会话在跑或有人的消息排队时返回 Busy；用本人时恢复失败报错，不新开会话。
- mock-agent，新文件 `tests/session_reuse.rs`：
  - run A 结束后以 run A 的主导新建 run B：run B 的 `planner` 就是这个会话本人（id 相同），没有新增 agent；run B 结束后它回到工作区。
  - run B 的 planner 用 `fresh: false` 把任务派给 run A 用过的会话：同一个 agent id 收到任务、cwd 是新任务的 worktree；任务合并后它回到工作区，`/v1/agents` 里还在。
  - 默认（不写 `fresh`）：新开执行会话，任务结束后被归档而不是删除，对话仍能读到；恢复后能用 `fresh: false` 再派给它。
  - **跨 run 抢同一个会话**：两个 run 同时用 `fresh: false` 派给同一个会话（`tokio::join!`），只有一个成功，另一个返回占用者。
  - **人的请求优先**：会话有人发来的消息在排队时，`fresh: false` 派活返回 Busy；人的消息先被处理。
  - **人打断执行**：执行中人点中断，执行标为 interrupted、占用释放、会话回到工作区，planner 收到通知。
  - **用本人恢复失败**：mock 驱动让这次 resume 失败，执行标为 failed 且写明上下文没能延续，没有新开会话。
  - **删除旧 run 不影响新 run**：会话先参与 run A，再被 run B 用本人占着；删除 run A 后，它的 cwd 仍是 run B 的 worktree，run B 的任务照常完成。
  - `move_cwd = false` 的驱动：`fresh: false` 被拒，提示改用新开。
- R1-B 的 `tests/delete_run.rs`、R1-A 的 `tests/work_start.rs` 按新语义改断言，例如「主导 agent 404」改成「回到工作区」。
- 真实环境补测一次（手动，记进本文）：Claude Code 会话在 worktree 里干完一轮，回到仓库根目录 `--resume`，对话完整；`claude --resume` 的列表里能在仓库目录下找到它。

**真实环境补测（2026-10-27，Claude Code 2.1.308，桌面版自带的 CLI，haiku）**：在 CLI 层做，命令与 `claude-native` 驱动一致（新开用 `--session-id`，换目录后在新 cwd 用 `--resume <id>`）；没有起一个接真实账号的 hub 走 `place`，hub 这一层由 mock 测试覆盖。

1. 临时仓库 `repo` 加 worktree `wt-a`，在 `wt-a` 里 `claude -p --session-id <id>`，让它记住口令 PELICAN-42。
2. 回到 `repo` 根目录 `claude -p --resume <id>`：答出 PELICAN-42，并说出上一轮在 `wt-a`、现在在 `repo`。**对话完整延续。**
3. `git worktree remove` 删掉 `wt-a` 后再在 `repo` 里 `--resume <id>`：仍答出 PELICAN-42。任务结束删 worktree 不影响本人接着用。
4. 会话文件的位置：`~/.claude/projects/` 下只有 `wt-a` 对应目录里有 `<id>.jsonl`（三轮都追加在这里），`repo` 对应目录里没有会话文件。所以 **`claude --resume` 在仓库根目录弹出的列表里大概率找不到它**（列表按当前项目目录列）；交互式列表这一步没法在非交互环境里点开确认，只看了文件。按 id 恢复不受影响，hub 一直按 id 恢复。若要让人在仓库根目录的 CLI 列表里看到，需要另做，见 §7 第 14 条。

## 5. 已定（2026-10-27）

1. **派活默认新开执行会话，复用必须显式指定**：`fresh` 默认 true，`fresh: false` 才用本人。「新开」只说明起点是干净的上下文，不代表用完删除；界面上叫「执行会话」。
2. **允许派活给人正在聊的会话，但不抢人的请求**：会话正在回人、或有人发来的消息在排队时，派活返回 Busy，由 planner 改选或稍后重试。会话空闲时可以接任务；接了任务之后人发来的消息排队，会话页显示「正在执行哪个任务」，并允许人中断。
3. **归档后不自动清理**：支持批量删除。归档释放运行资源、保留对话和执行记录，并且可以恢复，恢复后能接着用。

## 6. 顺序与工作量

1. §3.1 会话的家、占用表与 `place`：约 1.5 天，后面几步都依赖它。
2. §3.2 主导和 §3.4 收尾只释放本 run 的占用：约 1 天。做完后「run B 接着用 run A 的主导」就成立了。
3. §3.3 派活的 `fresh`、人的请求优先与中断，加 §3.6 名单：约 1.5 天。
4. §3.5 执行结果和 run 页参与者，加 GUI 侧栏改按 `home` 分组、会话页的「正在执行」与中断：约 1 天。

## 7. 实现差异

和上文方案不一致、或方案没写清楚而按下面处理的地方：

1. **从没开过会话的主导照样挪本人**。`lead_in` 的条件是「驱动 `move_cwd`，或这个会话从没开过」：没有会话就没有上下文要带，ACP 的新会话也可以挪，不必复制（R1-B 的「挪进去的主导」测试依赖这一点）。
2. **复制出来的主导在 run 结束时归档，目录留着它的名字**（2026-10-27 拍板）：finish 和 cancel 一样按占用表释放所有人，复制出来的主导（`role = lead`、`fresh`）也归档，对话和执行记录保留，人可以显式恢复。它的驱动只能在原目录恢复会话，所以归档时 cwd 不改回工作区，仍指向 run 的检出；检出本身随即删除（结束前已把没提交的改动提交到 run 分支），恢复时由 `lead_returned` 按 run 分支重建（分支已删就从 base 新建）。run 被删除后没有可重建的检出，`delete_run` 把 cwd 还指向它的会话改回工作区（上下文怎么办见第 15 条）。本人主导在 run 结束时回家，检出在它离开后删除（`checkout_vacated`，同样先提交）。已结束的 run 不再占着任何会话；R1-B「检出有未提交改动时删除要 force」现在出现在人恢复了复制的主导、又在检出里留下改动的时候，测试按这个改了。
3. **占用表多一列 `fresh`**：区分「本人」（释放后 `send_home`）和「执行会话」（释放后归档）。§3.1 的列里没有它。
4. **`place` 遇到任何排队消息都返回 Busy**，不只是人发的：停进程会撤回排队的消息。派活检查第 4 项单独判断「人的请求」，返回的原因写明是人在等。
5. **用本人时立即恢复**：`place(carry = true)` 停掉进程、改 cwd 后马上在新目录恢复会话，恢复失败当场报错（不等下一条消息、不走「开新会话」退路），并把会话送回家。普通聊天的退路不变；顺带修了退路里的一个错：新开的会话现在用自己的事件通道，失败那次进程的退出事件不再把它关掉。
6. **`fresh: false` 的检查分两段**：同一工作区、`move_cwd`、已归档三项与时机无关，在 `plan_submit` / `task_create` / `task_assign` 调用时就由工具返回原因；人在等、占用、额度三项在真正派出时检查，不满足时任务留在 pending、`progress` 写明原因、通知 issuer，下次调度再试（`task_create` 和 pending 状态下的 `task_assign` 在结果里列出 `not_started`）。恢复失败时还会在任务上记一张 `fresh: false`、`outcome: failed` 的交接卡，理由里写「上下文没能延续」。
7. **`fresh: false` 的 assignee 不限于 run 的团队**：可以是工作区里任何同角色的会话，包括已归档的执行会话（配 `restore: true`）。`fresh: true` 仍只认团队成员。
8. **执行会话重名**：执行会话归档后保留名字，同一个任务再开新的执行会话时取 `w-<run>-<key>-2`… 不再删旧的。
9. **`agent_retire` 改为归档**，`AgentHost::remove_agent` 删掉了；只有人从 API 删除会话时才真删。
10. **升级前的 run**：hub 启动时为仍在进行的 run 补占用（主导、未结束任务的 worker 和 reviewer），否则它们结束时没有可释放的行。
11. **中断接口**：`GET /v1/agents/{key}/execution`、`POST /v1/agents/{key}/execution/interrupt`。中断后任务转 stalled（审查中的转回 passed）。主导的占用不能中断，返回「停掉这一轮或取消 run」。
12. **交接卡的 `outcome`**：被打回后又被改派，保留「被打回」（`reassigned` 不覆盖已知结果）；同一个人返工后交付，改为「交付」。reviewer 不记交接卡。
13. **`home_of` 删掉后**，新 run 的基础分支取仓库当前分支，不再沿用上一个 run 的 base（两者通常相同）。
14. **会话文件不复制、不链接**（2026-10-27 拍板）：`send_home` 只把执行位置送回工作区。按 session id 恢复已经能延续完整对话，删掉 worktree 也不影响（§4 补测）；缺的只是 Claude 原生 `claude --resume` 列表里的可发现性。复制会留下两份同 id 的会话文件，之后追加到哪份、恢复选哪份都要验证；链接依赖 Claude 的内部存储布局。CrossAgents 保留原生 session id、继续按 id 恢复；「复制原生恢复命令」和「仓库根目录的原生会话列表可见性」列进 TODO §十五，后者先实测再定做法。
15. **恢复不能延续上下文时明说，不静默新开**（2026-10-27 补）：
    - 删除 run 时，cwd 还指向它检出的会话若有过会话、驱动又不能换目录（`move_cwd = false`），回工作区的同时记一个 `config.context_lost`（原因）。恢复它时会话页出警告「对话记录恢复了，但……：下一条消息会开新会话，不带原来的上下文」；下一次开会话不去另一个目录恢复，直接开新会话并再警告「这是新会话，没有带上之前的上下文」；新会话建立成功后才清掉标记，启动失败时标记留着，下次启动照样警告（测试 `a_lost_context_mark_outlives_a_start_that_fails`）。
