# S1：会话属于工作区，run 只记录谁参与过

状态：方案，待确认后开工。设计决定见 [DESIGN.md](../DESIGN.md) §4.7。

## 1. 起因

2026-10-27 讨论 run 的承接：run B 接着 run A 做，人选 run A 的 planner 当主导，希望由它决定是用新会话，还是用 run A 里用过的会话继续干活。run A、run B 在同一个工作区里，会话本应属于工作区。

现在的实现做不到，因为会话被 run 拥有：

| 环节 | 现在 | 位置 |
|---|---|---|
| 主导 | 用过的会话被**复制**一份放进 run 的集成工作区，从没开过会话的才挪本人进去 | `engine.rs::lead_in` |
| 派活 | 每个任务从队友**克隆**一个新会话，放进任务的 worktree | `engine.rs::fresh_agent`、`quota.rs::routed_worker` |
| 任务结束 | 克隆出来的会话被**删除**，对话一起没了 | `engine.rs::release_agents`、`tasks.rs::task_assign`、`review.rs` |
| run 招募 | 带 `spawned_by_run`，在数据上是 run 的附属 | `team.rs` |
| 删除 run | 主导副本和招募来的会话**一起删** | `delete.rs::owned_agents`（R1-B） |
| 送回原处 | 只为「被挪进去的主导」补了 `lead_home` | `delete.rs::send_home`（a567158） |

这些都基于一个错误前提，`lead_in` 的注释里写着："a vendor session cannot move"。实测并非如此：Claude Code 在别的目录 `--resume` 仍记得对话，Codex 的 `thread/resume`、`turn/start` 都能换 cwd（[claude-stream-json](../research/claude-stream-json.md) 第 42 行，[codex-app-server](../research/codex-app-server.md) 第 28 行）。

## 2. 目标

- 会话属于工作区。run 和任务通过执行记录（交接卡）关联会话，不拥有会话。
- run B 选 Pia 当主导，就是 Pia 本人，带着 run A 的上下文。
- planner 派活时可以选「用这个会话本人」或「按它的配置新开一个一次性会话」。
- 任务结束、run 结束、删除 run，都不删会话：本人回到工作区，一次性会话归档。

不做：跨工作区复用会话；同一个会话同时在两处干活；换账号时保留会话（会话存在账号目录里，换账号只能新开，靠交接卡延续）。

## 3. 改法

### 3.1 会话的家与执行位置（core、hub）

- `Agent` 加 `home: PathBuf`，即它所属的工作区。`cwd` 保留，表示当前在哪干活，平时等于 `home`。
  - 迁移：`cwd` 在 `<worktrees>/` 下的会话，按所在 run 取 `run.repo`；其余取 `cwd`。有 `lead_home` 的取它，然后删掉这个键。
  - GUI 侧栏按 `home` 分组（现在按 `cwd`）。
- 驱动能力加 `move_cwd: bool`：会话能在另一个 cwd 恢复。`claude-native`、`codebuddy-native`、`codex-native` 为 true，ACP 默认 false。
- `AgentHost::place(agent, dir)`：会话空闲时停掉进程、改 `cwd`，下一轮在新目录恢复（复用 runtime 现有「恢复失败就开新会话」的退路）。会话正在跑时返回 Conflict。`AgentHost::send_home(agent)` 就是 `place(agent, home)`。

### 3.2 主导（orchestrator）

- `lead_in`：选中的会话 `move_cwd` 为 true，且不在主导另一个未结束的 run，就 `place` 本人进集成工作区；否则才复制（保持现状作为退路），并在 run 上记一句为什么复制。
- run 结束（finish / land 之后 / cancel）以及删除时：主导是本人的，`send_home`。
- R1-A 的 `home_of` / `run_lived_in` 改成直接读 `agent.home`。`lead_home` 及 `delete.rs::send_home` 删掉，由 3.1 取代。

### 3.3 派活（orchestrator、协作工具）

- 规格里的 `assignee`（`plan_submit`、`task_create`）和 `task_assign` 的 `to` 接受两种写法：
  - `rex`：用 Rex 本人；
  - `rex` 加 `fresh: true`：按 Rex 的配置新开一次性会话（现在的行为）。

  默认值见 §5 第 1 条。
- 用本人时，hub 依次检查：同一工作区；`move_cwd`；没有在执行别的任务，也没有在主导未结束的 run；没在额度上被改派。不满足时，工具返回原因，由 planner 改选。通过后 `place` 进任务的 worktree。
- 一个会话本人只能同时挂在一个没结束的任务上（`Task.assignee`）。hub 在 `place` 前查一遍，和派活放在同一把 run 锁里。
- 额度改派（`routed_worker`）换账号时仍新开一次性会话，交接卡照旧。

### 3.4 收尾不删会话

- `release_agents`：本人 `send_home`；一次性会话 `archive_agent`（停进程、移出列表、保留对话），不再 `remove_agent`。这一条吸收 [SELF](SELF.md) 的 A3。
- `task_assign` 改派、reviewer 用完、`review.rs` 返工换人，同上。
- `delete_run`：不再删任何会话。主导和本人会话 `send_home`，一次性会话已经归档的保持归档。清单里 `agents` 改为列出「回到工作区」和「已归档」两类。`DeleteRunResponse` 相应调整，bindings 重新生成。
- `spawned_by_run` 保留，只作为来源记录（谁招来的），不再决定生死。

### 3.5 执行记录

- `Handoff` 加 `outcome: Option<HandoffOutcome>`，取值 delivered（交付）、reworked（被打回）、reassigned（被改派）、failed、cancelled。这次执行结束时回填到这张卡上。
- run 页「参与者」：按任务列出执行，每条链接到会话；已归档的一次性会话也能点开，只读。

### 3.6 planner 怎么知道有哪些会话可用

- 开场说明（`brief::kickoff`）的团队名单之外，加一段「工作区里的会话」：名字、模型、是否空闲、最近一次执行（哪个 run、哪个任务、结果），取自交接卡，最多列 12 个，按最近使用排序。
- `agent_list` 返回同样的字段。

## 4. 测试

- core / store：`home` 的迁移（`<worktrees>/` 下的会话归到 run 的仓库；`lead_home` 被吸收）。
- hub：`place` 对空闲会话生效，下一轮的 cwd 是新目录、session id 不变（mock 驱动断言收到的 resume 参数）；会话正在跑时返回 Conflict。
- mock-agent，新文件 `tests/session_reuse.rs`：
  - run A 结束后，以 run A 的主导新建 run B：run B 的 `planner` 就是这个会话本人（id 相同），没有新增 agent；run B 结束后它回到工作区。
  - run B 的 planner 把任务派给 run A 用过的会话本人：同一个 agent id 收到任务、cwd 是新任务的 worktree；任务合并后它回到工作区，`/v1/agents` 里还在。
  - 同一会话已在执行别的任务时再派给它：工具返回原因，任务没有被派出去。
  - `fresh: true`：新开一次性会话，任务结束后它被归档而不是删除，对话仍能读到。
  - 删除 run A：所有参与过的会话都还在（本人回到工作区，一次性会话保持归档），工作区和分支照 R1-B 的规则清理。
  - `move_cwd = false` 的驱动：用本人会被拒，提示改用 `fresh`。
- R1-B 的 `tests/delete_run.rs`、R1-A 的 `tests/work_start.rs` 按新语义改断言，例如「主导 agent 404」改成「回到工作区」。
- 真实环境补测一次（手动，记进本文）：Claude Code 会话在 worktree 里干完一轮，回到仓库根目录 `--resume`，对话完整；`claude --resume` 的列表里能在仓库目录下找到它。

## 5. 待定（开工前确认）

1. **派活默认用本人还是新开？** 建议默认新开，保持现在的隔离和并行；planner 要接着用某个会话时显式指定。另一种是默认用本人，忙的时候才新开，更省上下文，但并行任务会互相排队。
2. **人正在和某个会话聊天时，planner 能不能把它派去干活？** 建议能：消息照常排队，会话在 worktree 里干完回来再回人。GUI 在会话页顶部标出「正在执行 run B · 任务 c」。
3. **一次性会话归档后多久清理？** 建议先不自动清理，归档列表里能批量删除。

## 6. 顺序与工作量

1. §3.1 会话的家与 `place`：约 1 天，后面几步都依赖它。
2. §3.2 主导和 §3.4 收尾不删：约 1 天。做完后「run B 接着用 run A 的主导」就成立了。
3. §3.3 派活选会话和 §3.6 名单：约 1 天。
4. §3.5 执行结果和 run 页参与者，加 GUI 侧栏改按 `home` 分组：约 1 天。
